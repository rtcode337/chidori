# Chidori

日々確認したいニュースや趣味の情報を、利用者ごとの関心に合わせて収集・要約し、適切なタイミングで知らせるアプリです。技術情報に限らず、暮らし、スポーツ、エンターテインメント、地域情報などを扱います。

Elixir と Phoenix で実装しています。トップ（`/`）は最新情報の一般ニュースです。

## Chiezo との関係

Chidori は [Chiezo](https://github.com/rtcode337/chiezo) と利用者のあいだに立つ層です。Chiezo が知識と AI を持つ側で、Chidori がそれを人に見せ、人の意図を向こうへ渡します。

- Chiezo に溜まった情報を、読める形にして見せる（関連図・ニュース）
- 利用者の関心を Chiezo に伝える
- 何を集めてほしいかの指示を Chiezo に渡す（Chidori で読むものも、他のアプリで使うものも）

**名前は「知取（ちどり）」** —— 知を取って回る、千鳥のように各所を巡って拾う、を掛けています（Chiezo と並ぶ書き方で Chidori）。

**Chiezo で止めた収集も、画面から押した 1 回は走ります**（区画を指定して頼む・travel-log からの依頼・割り込み・「いま要約を作る」など）。AI の使い過ぎを気にして自動の回を止めていても、見て決めた 1 回は頼めるようにするためで、Chiezo に「人が押した 1 回」（`manual=true`）と申告して頼みます（`Chidori.Chiezo.by_hand/1`）。定時の時計（要約・情報収集）は申告しないので、止めた収集は時計では動きません。

**題材ごとの事情は Chidori が持ちます。** 「画家を集めてネットワーク図にする」のような文脈を Chiezo に持たせると、あちらが題材を選ぶ知識ベースになってしまいます。Chiezo は題材を選ばないまま置き、判断と見せ方はこちらに寄せる、という線引きです。

## トップページと設定

**トップページ（`/`）は、設定ページで選んだ枠をタブで並べます**（最初の枠が開いたときに出ます）。並べられるのは、要約を作る話題のいちばん新しい要約（全文を出し、右上のアイコンで全画面に開くと左右のスワイプで前後の要約へ）・その話題を興味トピックに絞った要約（「技術興味ニュース」など。トピックの網を育てる話題だけ）・技術イベント・お笑いイベントのこれからの注目イベント（注目度が高いもので、これから 2 か月のもの。お笑いイベントは数が少ないので中も出します）・関連図（画面ごと埋め込む）・技術書の未読の上位 10 冊（技術書の画面の頭にも同じ札を出します。オライリーの本は Kindle で読めないので別の枠に分け、こちらも 10 冊まで並べます。どちらの枠の札にも、オライリーも混ぜた総合の順位を「（総合 3位）」のように添えます。札には買う口のリンクを付け、オライリー以外は Kindle ストアの書名検索、オライリーの本は公式の頁へ飛びます）です。何も選んでいなければ一般ニュースの要約だけを出します。タブの列の右端の「…」を押すと、全部の枠を縦の一覧から選べます。枠の中を左右に払うと隣のタブへ移ります（長押しから文字を選ぶ指は払いにしません。全画面の要約の払いも同じ）。

**設定ページ（`/settings`）** は 2 つのタブに分かれています。

- **トップページ** —— トップに並べる枠と、その順番（開いたときはこのタブ）
- **Chiezo 収集** —— Chidori が Chiezo に頼んでいる収集の一覧です（巡回ごとの間隔・相手・前回・次回・走らない理由）。ワーカーの起きる間隔と 1 回に流す数、待っている回、取り込みの待ち行列も並べます（Chiezo の `GET /v1/collect/queue`）。**待ち行列が溜まってきたときに、何がどれだけの間隔で回っているかを 1 枚で読むため**のものです。収集は **Chidori の画面の並び**（最新情報の話題とそのトピック → 関連図 → データ収集と本棚）で、Chiezo にまだ送っていないものも並びます。**収集ごとに、巡回の相手と整理を自動で回すかを選んで「Chiezo に送る」で送れます** —— 送るのは各画面の「収集の設定を更新」と同じもので、Chidori の今の依頼文も一緒に届きます（`Chidori.CollectCatalog`）。**Chiezo の今の設定が Chidori の定義と違う収集には「Chidori の定義と違います」を出し、違う項目（依頼文・絵の拾い方・足りない巡回など）を並べます**（`Chidori.CollectDrift`）—— 直した依頼文が「収集の設定を更新」を押すまで届かないことに気づけるように。頼む相手と、止めた・動かしたは比べません。Chidori の画面に無い収集（Chiezo にだけ残っているもの）は後ろに並び、相手と整理だけを送ります（Chiezo の `PATCH /v1/collect/{name}/sweeps/{sweep}`）

## 関連図

`/relations` では、画家の影響関係・活躍年代と、芸能人（俳優・歌手・タレント・お笑い芸人）の夫婦・家族と、同じグループの仲間をネットワーク図で表示します。**最初に開くのは画家の図**です。どちらも Chiezo に名簿を持たせて育てる、同じ仕組みの図です。

**画家の図は [Chiezo](https://github.com/rtcode337/chiezo) に溜めます。** 「関連図を収集」を押すと、Chidori が Chiezo に**網羅の収集**を依頼し、その場で 1 回集めさせます。作られるのは止まった状態なので、最初の 1 回は Chiezo の管理画面で有効にしてから押してください（止まっている収集は Chiezo が断ります）。有効にすれば Chiezo が決まった間隔でも図を育て、Chidori はそれを読んで表示します。

**名簿・年代・様式は AI に書かせません。** Chidori が条件を言葉で書いて渡し、Chiezo がそれを抽出の指定にして、日本語版 Wikipedia から機械的に引きます（生没年のカテゴリから年代、「〜派の画家」などのカテゴリから様式）。AI が書くのは、そこに書いていないこと —— 影響関係と代表作と説明です。

**丸の大きさは知名度で決めます。** 使うのは日本語版 Wikipedia の月次ページビュー（bot 除外）で、これも Chiezo が収集の 1 件ごとに写してきます（`extra.pageviews_month`）。Chidori は収集を読むだけで図を描けます —— 画家 1 人ずつ引きに行っていた頃は、図を開くたびに数千回の往復が要りました。

**事実と判断は別の鍵に持ちます。** ページビューは機械が写す事実で、誰も書き換えません。日本語版の読まれ方が実態とずれている画家（海外で高名だが日本では読まれない、逆に最近の話題で一時的に読まれている）だけ、AI が倍率（`extra.fame_scale`）を書いて直します。同じ鍵を書き換えさせると元の値が失われ、Wikipedia を取り込み直しても新しいページビューを反映できなくなります。

**名簿は「〜の画家」で終わるカテゴリをまとめて指します**（`tag_suffix`）。書き並べると必ず取りこぼすためです —— 名前の付き方が揃っておらず（「イギリス」と「イングランド」は別のカテゴリで、中身は後者に寄っています）、書く側は思い出しで補うしかありません。**地域も年代も絞りません。** 葛飾北斎とゴッホが同じ図に並びます（ジャポニスムは実際の影響関係です）。

**指定を書けなかったときは収集を作りません。** 指定なしで作ると名簿が空のまま AI に肉付けを頼むことになり、数件だけの図ができて終わります。書けなかった理由は画面に出します。

**誰を見るかは AI に選ばせません。** Chiezo が名簿を区画へ割り、1 回に何区画かずつ渡します。選ばせていた頃は同じ人を何度も選ぶのを止められず、1 日 10 人では一周に何百日もかかりました。区画の切り方と巡回の並びは「画家の図の育て方」にあります。進み具合は画面でも Chiezo の管理画面でも「何区画のうちいくつ回り終えたか」として読めます。

**「ここが間違っている」は割り込みで頼めます**(Chiezo の `POST /v1/collect/<name>/focus`)。定時の巡回の進み具合には触らないので、待たずに直させられます。

**縦軸は年表になっています。** 丸は年代の順に等間隔で並ぶので、目盛りの間隔は一定ではなく、**画家が多い時代ほど広がります**。

### 図の操作

**関連図も区画の地図も同じ仕組みで動かします**（`assets/js/pan_zoom.js`）。引きずって移動、Ctrl+ホイールで拡大縮小、指 2 本でつまむ、＋ − 全体 全画面。図ごとに操作が違うと、画面を移るたびに覚え直すことになります。

- **引きずりはいつでも画面移動**です（丸や区画の上から始めても動きます）。込み合ったところで掴める隙間を探さずに済みます。動かさずに離したときは今までどおり選べます
- **拡大は `viewBox` を動かして行います。** 引き伸ばす（CSS の `transform`）と**寄るほど線が粗くなります** —— `viewBox` を狭めればブラウザが描き直すので、どこまで寄っても線は細いままです
- 図ごとの事情だけを足します（関連図は `assets/js/relation_map.js` —— 年代と地域の札を画面の端に留める、見ている範囲をサーバーへ知らせる、探した人へ寄る）

**実行のたびに全部を作り直すのではなく、少しずつ良くしていく形**です。1 回で仕上げようとせず、抜けている画家を足す・説明の粗いものを書き直す・粒度を揃える、といった直し方を頼みます。触れなかったものはそのまま残り、消えるのは AI が消すと明示したときだけです。

**図の構造は Chiezo に持ち込みません。** 向こうにあるのは「1 画家 = 1 文書」の普通のソースで、属性と関係はタグに載せてあります。

| タグ | 意味 |
| --- | --- |
| `画家` | この図に取り込む目印 |
| `様式:ポスト印象派` | ノードに添える様式 |
| `年代:1880-1890` | 生年-没年(西暦の数)。ノード下の年代帯・並び順と、Chiezo の区画はこの最初の数で決まる。存命は `1948-`、推し量った年は `1720頃-1790` |
| `影響元:クロード・モネ:光と色彩` | その画家から受けた影響。線になり、線を押すと何を受けたかの説明が出る |

ノードとエッジという読み方を与えるのは Chidori 側です。判断や見せ方を Chiezo に持たせない、という線を崩さないための形にしてあります。

### 見た記録

**丸を押して開いた先で、「見た」印とメモを残せます。** 画家の展覧会へ行った、この絵を実物で見た、といった記録は収集には書きません —— あちらは題材も好みも持たない側なので、利用者ごとの事情は Chidori の置き場（Chiezo の名前付きの置き場 `chidori_data`。下の「利用者が書いたことの置き場」）に持ちます。印の付いたノードは図の上で**橙色の枠**になります（巡回で動いたものの緑の破線とは別の見え方にしてあるので、自分が付けた印かどうかが読み分けられます）。

残るのは「見たかどうか・いつ・ひとこと」の3つで、**1 ノードにつき 1 件**です。印もメモも空にして保存すると記録ごと消えます。**これは暫定の形**で、同じ画家を何度も見に行く記録（展覧会ごとに 1 件）が要るようになったら、この表を親にして子を足す形へ広げます。

**図を開くたびに Chiezo へ聞きに行きません。** 8,000 人ぶんを読むので数秒かかるのに、Chiezo の側は数時間に 1 度しか動きません。見出しの下に**最後に取得した時刻**が出るので、取り直すかは読む人が決めます（「最新の情報を取得」）。**図を読むときは Chiezo の収集の設定（巡回・区画・依頼文）を読みません** —— 設定は図の下の「画家の影響と時代の設定」（見出しを押すと開きます）を開いたときに読み、読み終えるまでは「Chiezo から情報を取得しています」とだけ出します。

図の左上には**名前で探す欄**と、その隣に**見た画家を選ぶ一覧**が出ます。名前を思い出せなくても、印を付けたところへは戻れます（並びは見た日の新しい順。図に出ていないものは並びません）。

**AI がまだ目を通していない画家も図に出します。** 機械で名簿に入っただけの人は**薄い札**になり、図の下の「レビュー済みだけ」「未レビューだけ」で片方だけに絞れます（Chiezo の読み口は既定で未レビューを外すので、`include_removed` で受け取り、消えたものだけを Chidori 側で落とします）。

**図の器は図と同じ縦横比にします。** 画家の図は縦に長いので、画面の高さで切ると拡大しないと下が見えず、全体を入れようと縮めると札が小さすぎて描けません。拡大していない状態で全体が入り、はみ出すぶんはページのスクロールで見ます。

**線の上には文字を置きません。** どの線の説明か読めず、札に重なるためです。線を押すと、AI が書いた「何を受けたか」、受けた側の説明で相手に触れている文、2 人の年代・地域・様式の比較、ほかの影響元が出ます。

**関連の相手は、実在する見出しに限ります**（収集の `verify_tags`。Chiezo が焼く前に落とします）。**代表作は照らしません** —— 作品が単独の記事を持つことは少なく、照らしていた頃は AI が目を通した画家の 9 割で代表作が落ちていました。

**画家を押すと、その人の記事の先頭画像（たいてい自画像か肖像写真）を説明の横に小さく出します。** 引き方は代表作と同じで、無ければ何も出しません。

**代表作は、説明も絵も Chiezo から引きます。** どちらも jawiki に入っています（取り込みが `page_props` ダンプから代表画像を拾って `extra.image` に入れます）。長期記憶を取り込み直す前は画像が入っていないので、**そのあいだだけ**日本語版 Wikipedia に聞きます（入れば通らなくなります）。**結果は 1 日覚えます**。絵が見つからない作品（記事の無いもの、近年のもの）は、**画家名と題名で引く Google 画像検索へのリンク**にします。絵は原寸ではなく縮小したものを指します。

### 画家の図の育て方

収集は **3 つの巡回**に分かれていて、**順番に意味があります**（後のものは前のものが一周するまで走りません）。

| 巡回 | やること | いつ |
|---|---|---|
| 名簿 | Wikipedia のカテゴリから機械的に名前を集める（AI は使わない） | **一度きり**（取り込み直したら押す） |
| ざっと | **年代と地域**を最優先で埋める。ついでに説明・代表作・様式も。明らかに画家でない人は消す | 2 時間ごと・**一周したら止まる**（6 日ほど） |
| 調査 | 区画ごとに、漏れを足す・内容を磨く・要らないものを消す | ざっとが一周してから。12 時間ごと・**一周 40 日** |

**区画は「地域 × 生年」で切ります。** 辞書順で切っていた頃は「Kage〜おおやちき」のような塊になり、同じ区画に入った 2 人に何の関係もありませんでした。**1 年より細かくは割りません** —— 分けると「この範囲の全員」が並ばなくなり、漏れを問えなくなるためです（人の少ない地域は年の幅が自然に広がります）。

**年代と地域が空だと区画が決まらない**ので、その人は「年代不明」の置き場に入ります。そこを埋めるのがざっとの最優先の仕事で、埋まれば本来の区画へ移ります。

**区画の一覧は「画家の影響と時代の設定」の中にあり、全区画を出します。** 「ざっと見る」と「整理」がそれぞれ最後に見た時刻を列で並べ、まだ見ていないものが先に並びます。見出しは「区画（見終わった数 / 総数）」で、見終わった数はざっと見るが一周するまではざっと見るの、一周したら整理のものです（食事処の区画の一覧も同じ形）。**行の「ざっと見る」「整理」を押すと、その区画をその回として先に見てもらえます**（印が付くので、巡回が同じところをもう一度見ることはありません。見終わった区画も頼み直せます）。

**「ざっと見る」で頼むと、AI が目を通した人の未レビューの印が外れます。** 未レビューの画家を開いたときも、その人の区画を同じように頼めます（区画は押したときに割り出します）。区画の所属は、Chiezo と同じ規則で Chidori 側で割り出しています（`Chidori.Relations.Partitions`）。

**割り込みも調査の回に頼みます**（専用の巡回は置いていません）。画家を名指しした割り込みは区画に印を付けず、区画を名指しした割り込みは印を付けます。

**消えた画家は、同じ設定の中の「消えた画家」に理由と日時つきで並びます**（図には出ません）。消し間違いなら「戻すよう頼む」で、その人を名指しして整理の回に確かめ直してもらえます。割り込みは「書かれた指示にだけ従う」回なので、区画の「整理」も戻す頼みごとも、してほしいことを全部指示に書いて送ります。

**芸能人の図も、画家と同じ仕組みで育てます**（`Chidori.Relations.People`。収集 `chidori_people`。`CHIDORI_PEOPLE_COLLECTION` で変えられる）。**いちばん知りたいのは夫婦**で、親子・きょうだいとグループのメンバーがそれに続きます。名簿は**人だけ**で、日本語版 Wikipedia のカテゴリ（俳優・女優、歌手、タレント、お笑い芸人）から機械で取り込み、カテゴリから `種別:<俳優/歌手/タレント/お笑い芸人>` を付けます（色と区画の材料なので、AI に判断させない）。**グループ（コンビ・アイドルグループ・バンド）は名簿に入れません** —— 入れていた頃は、ざっと見る回がグループの文書ばかり回って人が育たなかった。**名簿は知名度で下を切ります**（Wikipedia の月の閲覧数。始めは月 1 万以上で約 3,000 人。表 `relation_settings`）—— カテゴリだけで 3 万人に届くためで、図の設定欄の「名簿の広さ」で下げて「名簿を引き直す」を押すと広がります（足すだけで、上げても名簿からは消えない）。AI には年代（人は生年、グループは結成年）と、`家族:<相手>:<配偶者/元配偶者/親子/きょうだい>`・`グループ:<今所属しているグループの記事名>` を足させ、**夫婦は一人ずつ確かめて両側に書かせ**（両側に書くのは同じ回に並んだ人どうしだけ。並んでいない既存の人の文書は Chiezo が置き換えずに弾くので返させない。線は片側に書けば引ける）、**相手が名簿にいなければ名簿の外からも足させます**（日本語版 Wikipedia に記事のある有名人なら芸能人でなくてよい。種別は `著名人`。知名度で切ると相手が抜けるため）。**公表されている関係だけ**を書かせ、**未成年の家族と、記事の無い家族（一般の人）は書かせません** —— 名簿にいない相手への線は出ない仕組みなので、一般の人を名簿に足させないことで守ります。図は縦が年代で、**横の帯は持ちません**（種別は札の色で分かる。帯に割ると夫婦が左右の端に離れる）。**グループは同じ `グループ:<名前>` を持つ人を囲む枠**で描き（名簿にいるメンバーが 2 人以上のとき）、メンバーの生年の中ほどの高さに 1 かたまりで置きます（名前は枠に書く）。行の中は、つながっている相手の真上・真下へ寄せます。夫婦は太い赤の線、家族は実線です。**顔写真**は記事の Commons の写真を、Chidori が 1 人 1 回だけ小さな縮小版（横 120px）で取りに行って DB（`face_thumbs`）に写し、`/faces/:id` から配ります（見る人のブラウザに写真の置き場を直に引かせない。1 枚ずつ間を空けて取り、取れなかったことも残す）。押すと Commons のファイルのページ（出典とライセンス）へのリンクが出ます。図の読み方の違い（札の種類・帯・色・枠・線にするタグ）は `Graph.from_docs/2` に渡す仕様に寄せてあり、画家の図はその既定です。

AI の応答に出典が付いていない関係、実在しないノードを指す関係、`http`/`https` 以外の出典は取り込みません。連続して押したときは間隔を空けます。

## 最新情報

`/news`（トップの `/` も同じ画面）では、[Chiezo](https://github.com/rtcode337/chiezo) の「集める」層に収集を依頼し、溜まったものを読みます。集めるのは Chiezo で、Chidori は依頼と閲覧だけを持ちます。定期実行の時計も、AI の呼び出しも、集めたものの置き場も、すでに Chiezo にあるためです。

**話題ごとにタブで分かれています**（いまは「一般ニュース」「技術ニュース」「技術イベント」「お笑いイベント」「映画」「アニメ」「市況ニュース」。**先頭のものが最初に開きます**。タブは見出しの上にあります）。**話題は Chidori の機能**で、関連図の「画家」「芸能人」と同じ立ち位置です。集め方も関心も話題ごとに違うので、定義は `Chidori.Topics.defined/0` にあります —— 足すときはそこへ 1 つ書けば、タブも収集も増えます。**収集も溜まったものも話題ごとに別**なので、片方を読み直しても、もう片方の状態は入れ替わりません。

**何を集めるかは、話題の「関心」から作ります。** 話題ごとに本文を丸ごと持たせると、話題を足すたびに同じ形の文をもう一度書くことになるためです。関心と名前は定義の側が持ちます（依頼済みの収集の文面を直すのは Chiezo 側から）。

**古くなり方も話題で違います。** ニュースや記事は日が経てば要らなくなるので期限で落としますが、**技術イベントは「終わったかどうか」だけが古さ**です —— 半年先のイベントを 30 日の期限で落とすと、いちばん要るときに消えます。そういう話題も収集の種類は流れですが（これから開かれるものを次々と集めていくので）、期限だけ外し（`ages_out: false` → `keep_days: 0`。Chiezo の期限は配信日で数えるため）、終わったものを整理の回に落とさせます。イベントでは 1 件ごとに**開催日・場所・申込先**を書かせます（この 3 つが無いと、読む人は行けるかどうかを決められません）。

**技術イベントは要約を作らず、開催日のカレンダーを出します**（`digest: false` / `calendar: true`）。イベントは読み物ではなく「いつ・どこで・行く価値があるか」で選ぶものだからです。整理の回に、並んだイベント全部へ `開催日:YYYY-MM-DD`・`開催地:<都道府県 / オンライン>`・`注目度:高/中/低` のタグを付けさせ、カレンダーはその月の `開催日:` タグで引きます（溜まっている全部は読みに行きません）。マスには注目度が中以上のものを高い順に色付きで並べ、低いものは件数だけに畳みます。**札の頭には開催地を出し**（「東京」「大阪・オンライン」）、**海外は「海外 アメリカ」と添えて破線の枠と青い字で分けます**（都道府県でもオンラインでもない開催地を海外とみなす。国内の会場もあれば国内）。開催地で絞れ（「国内」「海外」でまとめても選べる）、日を押すとその日のイベントが全部並び、**それぞれの下に簡単な説明を出します**（本文の頭から日時・場所の行とタグを落として 200 字まで。名前を押すと申込ページへ）。タグが付く前でも、connpass の本文の頭（`開催日時:` / `開催場所:`）から日付と都道府県は読めます。

**映画は 1 件 = 1 作品です**（`works`。`Chidori.News.Movies`）。記事を溜めると同じ作品の記事が何本も並び、公開日も注目度も口コミも作品ごとにまとまらないので、配信元は持たず、巡回は 2 つだけにしています —— **情報収集**（1 日に 1 回。いま公開中の作品と、3 か月先までに日本の劇場で公開される作品を、公開日が決まったものだけ足す。**1 回に探すのは「公開中・今月・来月・再来月・3か月先」のうち 1 区切りだけ**で、次の区切りは AI に返させて Chiezo のカーソルに覚えさせる —— 劇場公開は週に 20 本を超え、全部を 1 回で頼むと途中で打ち切られるため。対象は全国規模の公開作と、小規模でも話題の作品）と**整理**（12 時間ごと。今ある作品を本文ごと見て、公開日と注目度を付け直し、**注目度が高い公開済みの作品に口コミの傾向と興行成績**を出どころの URL つきで書き足し、公開から 60 日経ったものを落とす）。口コミは本文を写さず傾向を書かせ、結末も書かせません。書いた日を `口コミ:YYYY-MM-DD` のタグに残させ、公開から 1 か月の間は 7 日ごとに取り直させます。画面は技術イベントと同じカレンダーを `公開日:` のタグで引き、その下に**注目作**（注目度が中以上。公開中は注目度の高い順、これからは公開の近い順）を口コミまで並べます。記事一覧はありません（`articles: false`）。**作品の絵（ポスター）も出します** —— 情報収集の回に公式サイトの画像の URL を返させ、**Chiezo が 1 回だけ取って縮めて持ちます**（Chiezo の収集の `thumbs`）。画面が公式サイトの絵をそのまま指すと、見る人のブラウザが開くたびに外のサイトへつなぐためです。AI が絵を返さなかった作品は、公式サイトのページの `og:image` を Chiezo に拾わせます（`thumbs: %{pages_from: ["*"]}`。ホストは問わない。アニメ・お笑いイベントも同じ）。技術イベントも同じ形で、connpass は配信に絵を載せず、外から足したイベントは主催ごとに公式サイトが違うので、どのホストのページも読ませます。TECH PLAY は配信の絵をそのまま使います。

**映画の要約は、映画館の販促記事の調子で書かせます**（1 日 1 回くらい。時刻は画面で決める）。材料は前回から入ったものではなく、いま入っている作品ぜんぶで（要約を起こすときの指示も同じ。最後に探した区切りの作品に寄せない）、章は「今週公開の注目作」「公開中でいま評判の作品」「もうすぐ公開」のように観に行く予定が立てやすい並びにします。書き出し・材料・調子は話題ごとに書き分けられます（`digest_intro` / `digest_material` / `digest_tone`）。

**公開中か、1 週間以内に公開される作品の札には「近くの上映館を Gemini に聞く」を出します。** 押すと Google 検索の AI モード（`udm=50`。Gemini が答える）を、近い映画館と今日・明日の上映時間を聞く質問文を入れて開きます。現在地は押したときにブラウザから取って添え（https で開いているときだけ取れる）、取れなければ現在地を書かずに聞きます。**映画の要約（トップページの枠と全画面）にも、章で紹介した作品ごとに同じリンクを添えます**（章の出典として引き直せた作品の名前で聞く）。

**アニメも 1 件 = 1 作品です**（`works`。`Chidori.News.Anime`。映画と同じ形）。追うのは今期（いま放送・配信中）と来期のテレビアニメと配信アニメの新作で、劇場アニメ・再放送は入れません。**情報収集**は 1 日に 1 回、「今期・月火 → 今期・水木 → 今期・金土 → 今期・日曜と配信のみ → 来期」の 1 区切りずつ探します（今期は 1 期で 50〜70 本あり、1 回では返しきれないので曜日で分ける）。**整理**は放送日と注目度を付け直し、注目度が高い放送中の作品に評判の傾向を書き足し（`評判:YYYY-MM-DD`。7 日ごとに取り直し、最終回のあとにもう 1 回）、最終回から 30 日経ったものを落とします。タグは `放送開始:`・`放送終了:`・`期:`・`曜日:`・`放送:`・`配信:`・`注目度:` で、カレンダーは `放送開始:` で引きます。要約はアニメ雑誌のおすすめ特集の調子で書かせます。話題になった作品をまとめて観る読み方に合わせて、放送が終わったばかりの作品と放送中の作品を主役にし、これから始まる作品は注目度が高いものだけを添えます。

**お笑いイベントは、技術イベントと同じカレンダーで出します**（`Chidori.News.ComedyEvents`）。賞レース（予選・準決勝・決勝とその放送）、お笑いの特番、事務所や劇場の大型公演・フェス、芸人の単独ライブとツアーを入れ、**テレビ番組も放送日で 1 件のイベント**にします（`開催地:テレビ` / `開催地:配信`。オンラインと同じ扱いで、海外には数えない）。お笑いのイベントを機械で配っている先が無いので配信元は持たず（溜める回も置かない）、**情報収集**（1 日に 1 回、今月から 3 か月先までを 1 か月ずつ。`look_ahead` にモジュールを書く）だけで集めます。**整理の回は置きません** —— 外を探して足すのは情報収集と重なり、AI の回が 1 日 2 回になっていたので、終わったイベントを消す・タグを揃えるのも情報収集の回にさせ（足すだけの回にしない）、割り込みもこの回で走らせます（`News.focus_sweep_of/1`）。タグは技術イベントのものに、`種類:賞レース/特番/ライブ/単独ライブ` と `出演:<芸人>`（主な出演者を 5 組まで。Wikipedia の見出しの書き方で）を足しています。

**先の月は、1 日に 1 回の「情報収集」の回が埋めます**（足りないものを外から探して足す仕事）（`look_ahead: true`）。connpass の新着は募集が出たものしか流れてこず、勉強会の多くは 1〜2 か月前に募集を出すので、そのままではカレンダーが来月で止まります。この回は今日から 6 か月先までを **1 回に 1 か月ずつ**（今月 → 来月 → 2か月先 → … → 6か月先 → 今月 と 7 日で一周。次の月は AI に返させて Chiezo のカーソルに覚えさせる —— 6 か月ぶんを 1 回で頼むと途中で打ち切られるため。整理の回にはカーソルを返させない）、日程を早くから出す大きなイベント（各社の年次カンファレンス、毎年開かれるコミュニティのカンファレンスなど）を探して足します。いま入っているものの見出しを見せて、同じものを足し直させません。**技術ニュースで選んだ興味トピックの分野のイベントも、大きさを問わず探させます**（技術イベントには興味トピックを選ぶ図が無いので、技術ニュースのものを使う。`interests_from`。技術ニュースで選び直すと、技術イベントの依頼文も送り直します）。**整理の回の外探しも、技術イベントでは頼み方を変えています**（`outside`）—— 話題に共通の文は論文やテックブログを探させるので、代わりに connpass 以外で告知されるイベント（公式サイト、Doorkeeper・TECH PLAY・Peatix など）を探させます。

### 流れを追う収集です

Chiezo の収集には**種類**があります。最新情報は**流れ** —— 時とともに増えるものを追っていて、直近だけが対象で、**古いものは順に要らなくなります**（既定で 30 日ぶんを持ち、それより古いものは焼き直しのときに落ちます）。関連図は**網羅**で、ある括りの全部が対象です。増減はしても古いものが要らなくなることはないので、期限では落としません。

### 収集は仕事ごとに分かれています

関連図と同じく、Chiezo に置く収集は**巡回**に分かれています。1 つの文で全部を頼むと、どの回も同じ薄さの仕事になるためです。画面（`/news`）の「Chiezo の収集」の枠で、巡回ごとに頼む相手とモデルを選んで送れます（モデルの候補は相手ごとに違うので、相手を選び直すとそちらのものに入れ替わります）。**考える量の欄はありません** —— Chiezo 側でモデルの名前に畳んであります（`sonnet-high` のような形）。

**ワーカーも相手の選択肢に並びます**（「ワーカー」の見出しの下）。1 つの相手に固定で頼むのではなく、**枠に余裕のある相手へ振り替えながら回す**並びです。選ぶとモデルの欄は消えます —— 渡す先がそのときの枠で決まるので、モデルを 1 つ選んでもどの相手に対する指定なのかが決まりません。

| 巡回 | やること | AI |
|---|---|---|
| 見出し / 集める | 溜める回。配信元があれば RSS / Atom から機械的に、無ければ AI に集めさせる | 配信元があれば使わない（相手も選べません） |
| 整理 | 前回から入ったものを読んで重要度と分野のタグを付け直し、宣伝や的外れなもの・重複を落とし、**そのうえで**配信元が拾わなかったものを外から探して足す（ニュースだけでなく、話題の記事や論文も） | 使う |
| 要約 | 前回から入ったものを 1 件のレポートにする（要旨・要点・章・表・出典に分かれた読み物）。**時計を持たず、Chidori が起こしたときだけ動く** | 使う |

**整理は定時でも回します**（どの収集も 12 時間ごと。`Chidori.SweepNames.tidy_minutes/0`）。まとめの直前にもう 1 回起こしますが、それだけにすると、落とす仕事も外を当たる仕事もまとめの回数ぶんしか走りません —— ニュースは新しさが落ちると意味が薄いので、間を空けすぎないためです。

**論文は依頼文で名指しして念を押しています。** 外を当たる先の 1 つとして箇条書きに並べていただけの頃は、実測で 269 件のうち論文が 2 件しか入りませんでした —— 4 つ並んだうちの最後の 1 行では埋もれます。配信元は論文を配らないので、**この回が見に行かなければ永遠に入りません**。件数は求めていません（「必ず N 件」と書くと数合わせで薄いものが入り、重要度の印が意味を失うためです）。

**漏れを探す回は分けていません。** 分けていた頃は、重なった時間ぶんを 2 度読ませていました（外を当たる回は直近 4 時間、印を付け直す回は直近 6 時間）。画家の収集が同じ理由で 1 本にまとめてあります（あちらは同じ区画を 3 回渡していました）。**外から見つけたものに、既にあるものを上書きさせない**のだけは依頼文で頼んであります —— 見出しが同じものを薄い要約で返されると、付いている印ごと置き換わるためです。

**記事一覧は公開の新しい順の窓です**（直近 3 日。薄ければ新しい順に 20 件まで埋め、80 件で切る）。Chiezo の新着の口から読み直して並べます —— 収集の見本は更新の新しい順で、整理が触るたびに進むので、そのまま並べると「直近の整理で AI が触った順」になっていました。**並びは選べます**（重要度順・新しい順・反応の多い順・興味の近い順）。**反応の多い順ははてなブックマーク数の実数**で、キー不要の件数 API から 50 本ずつ引き、1 時間覚えます（AI が付ける話題度は推し量りなので、並びには使っていません）。

**一般ニュース・技術ニュース・技術イベントは配信元を持っています**（一般: NHK（主要・社会・政治・経済・国際）・朝日新聞・Yahoo!ニュース / 技術: Publickey・ITmedia NEWS・InfoQ Japan・CodeZine・Zenn・Qiita・はてなブックマーク・Hugging Face Daily Papers / 技術イベント: connpass の新着・TECH PLAY）。**Hugging Face Daily Papers は JSON の API しか配っていない**ので、どの項目を読むかを書いて Chiezo に引かせています（`json`。話題の論文が、整理の回の外探しに頼らず毎回入る）。見出し・要約・URL・配信日は機械が正確に取れるので、AI の枠は「何が重要か」「どうまとめるか」へ回します。ニュースと記事は同じ収集に溜まりますが、`ニュース` / `記事` のタグで分けて取り出せます。

**整理の回の頼み方も話題ごとに書き分けます** —— 外を当たる先（`outside`。一般ニュースは官公庁や他の報道機関、技術は論文やテックブログ）、話題度の人気枠（`buzz`。一般ニュースは各社のトップや総合の人気エントリー、技術ははてブの IT や Qiita）、トピックの網の例（`theme_examples`）。共通の文は技術向けに書いてあるので、書き分けないと一般ニュースでも論文を探しに行きます。

**機械収集の間隔は話題ごとに変えられます**（`every`。技術イベントは配信元を毎時見る）。**整理の間隔はどの収集も 12 時間ごとにそろえます**（既定。設定ページの「Chiezo 収集」の「巡回の間隔」で、ざっと見るの間隔と一緒に変えられます。保存すると Chiezo の該当する巡回に間隔だけを送り、区画を回る巡回は一周の日数も同じ比で伸ばします）—— 収集ごとに 4 時間・12 時間・1 日と散らばっていた頃は、ワーカーの待ち行列が溜まってきたときに何がどれだけ積まれるのかが読めませんでした。6 時間ごとにしていた頃は、整理を引き受ける相手の 7 日枠が回復より速く減っていたので延ばしました（AI が目を通すまで画面に出ないニュース類は、そのぶん最長 12 時間遅れて出ます）。**整理を自動で回したくない収集は、同じページの収集の表で「自動で回さない」にチェックを入れて送ると止まります**（Chiezo の巡回の時計だけを外す `by_caller`。巡回は残るので、割り込みや travel-log からの依頼では今までどおり走ります）。選んだものは Chidori が覚えていて（表 `tidy_stops`）、収集の設定を送り直すたびに載せ直します。

**その話題ならではの頼みごとも書けます**（`note`。整理の回の依頼文に足されます）。関心が「何が読む価値があるか」なのに対して、こちらは「1 件ごとに何を書き足すか」です。技術イベントでは、並んだイベント全部に開催日・開催地・注目度のタグを付けさせています。

**整理はまとめに触りません。** まとめは同じ出来事に触れているので重複に見えますが、落とすと画面と通知からまとめが消えます（実際に消えました）。依頼文で「`まとめ` のタグが付いたものには触らない」と頼んであります。

**消えたものと、まだ整理が読んでいないものは画面に出ません。** Chiezo は消したものを消さずに印（`_chiezo_removed`）を付けて残し、機械で引いたばかりのものにも印（`_chiezo_unreviewed`）を付けます。**落とすのは Chiezo の側**で、どの読み口でも既定で外れます —— Chidori が選り分ける形にすると、印が増えるたびにこちらも直して回ることになり、しかも漏れるのは読者の画面だけなので気づくのが遅くなります。

**まとめは直近の窓から拾いません。** タグで引き直します —— 見出しの回が 60 件足すと、まとめは直近の一覧から押し出され、**まとめが出ない時間帯ができます**。

**溜めるところは機械、選り分けるのは AI**という分担です。配信元から機械的に取り込むぶん、宣伝記事も的外れなものも混ざるので、落とすのは整理の回の仕事にしてあります（落とす力を持つのはこの回だけ）。**消したものは Chiezo が覚えていて**、同じ見出しが次に流れてきても戻りません。

**同じ記事を二度足させません。** 既に入っているかは**見出しではなく URL で**確かめさせます —— 同じ記事が配信元ごとに違う見出しで流れてきますし（「記事名 - サイト名」と「記事名」）、整理の回に差し込まれるのは前回から後に入ったぶんだけです。**見出しの付け替えもできません**（別の見出しで返すと、同じ URL の 1 件として Chiezo に弾かれ、元の見出しのまま残ります）。**まとめは記事の URL を名乗りません** —— 引いた記事の URL を入れると、その記事が既にあるぶんと同じ 1 件とみなされ、まとめ自体が入りません（出典は本文に書きます）。

**記事に絵が付くことがあります。** 配信元がフィードで配っているぶんだけです（ページを取りに行くのは本文を取ることになるのでしません）。実測では、はてなブックマークと Zenn が配っています。

**まとめはレポートとして出ます。** 画面（`/news`）の先頭の「要約」に出るのは、要旨・要点・章・表・出典に分かれた読み物です。**ページの上に出すのは見出し・要旨・目次までで、章と出典は押して全画面で読みます** —— 長いまとめを全部広げると、下の話題と記事一覧が遠くなるためです。目次の項目を押すと、全画面でその章から開きます。全画面では**左右に払うと前後のまとめへ**動きます。**古いほうを左に置きます**（右へ払うと古いほう、左へ払うと新しいほう）—— 右へ払うのはふだん「戻る」の動きなので、戻る先を古いほうに揃えています。上の帯のボタン（← 古い / 新しい →）と ←→ のキーも同じ向きで、Esc で閉じます。本文を最初から持っているのは最新の 1 件だけなので、前のまとめは開いたときに Chiezo から引き直します。溜まったものをそのまま並べても読めないので、何が起きたかと、なぜ押さえるべきかを先に言います。**章の番号と目次と出典一覧は画面の側で付けます** —— 本文に書かせると、章が増えた回に番号がずれます。

**出典は記事の見出しでリンクになり、章にはその記事の絵が 1 枚だけ付きます。** まとめには `出典: [記事の見出し](URL)` の形で書かせ、Chidori はその見出しで Chiezo から記事を引き直します —— 画面に並んでいる直近のぶんと突き合わせる形にはしていません。まとめは前回から今回までに入った全部から引くので、そこに収まる保証がないためです（実測では、直近 20 件との一致は 13 本中 0 本、50 件でも 7 本）。**見出しは Chiezo の中で 1 件を指す鍵**なので、引き直せば窓の大きさに関係なく当たります。絵は配信元がフィードで配っているぶんだけなので、付かない章もあります。

**一覧は重要度の順に並びます。** 記事は「記事一覧」の見出しの下に、ふだんは畳んで置いてあります（読むのは要約と話題の網で、1 件ずつを拾いに行くのは気になったときだけのため）。開くと 1 件ずつが「優先 / 注目 / 急がない」の順で並びます。同じ重さのものは新しい順のままです。**低いものも消しません** —— 重要度は並びであって、ふるい分けではないためです。

**重要度は AI が付けた印が先です**（`重要度:高` などのタグ）。付けるのは整理の巡回で、読んだうえでの判断です。語の一致だけで決めると、同じ語を含むだけの 1 件が上に出ます。印が無いものだけ、見出しの語で見ます（災害・避難・金融政策など）。

**どれだけ反応されているかは別の軸で持ちます**（`話題度:高` などのタグ。整理の巡回が付けます）。重要度に混ぜると、**話題になっていないが効く 1 件**と**効かないが沸いている 1 件**が同じ印になり、どちらの読み方もできなくなります。**数は持ちません** —— 配信元は反応の数を配らないので、付けるのは読んだ AI の判断です（同じ出来事を何本の媒体が報じているか、人気枠から入っているか）。印の無いものには何も出しません（まだ読まれていないだけの 1 件が「話題になっていない」として並ばないように）。

**押す口は「Chiezo の収集」の枠にある 1 つだけ**です（関連図と同じ形）。収集がまだ無ければ**止まった状態で**作り、あれば画面で選んだ設定を送り直します。**走らせはしません** —— 動き出すのは Chiezo の管理画面で有効にしたときだけなので、**この画面から AI が勝手に動くことはありません**。有効にすると Chiezo が巡回ごとの間隔で集め、Chidori はそれを読みます。

定時の巡回とは別に頼みたいことがあれば、記事を押して開く詳細の「この記事について Chiezo に頼む」から 1 回だけ走らせられます（巡回の進み具合にも次の予定にも触りません）。**走るのは整理の回です** —— 専用の巡回は置いていません。頼まれるのはたいてい「これは宣伝だから落として」「この印が違う」で、**落とす力と印を付け直す力を持つのはこの回だけ**だからです。

### 市況ニュース（売買提案のアプリ が読む）

**記事の集め方は技術ニュースと同じ**です（配信元の機械収集 → 整理。NHK 経済・Yahoo!ニュース 経済・JPX のお知らせ・はてブの経済）。関心は「日本株の株価に影響しそうなもの」で、整理の回が記事に出てくる上場企業の**証券コード**（`銘柄:7203`）と**区分**（`区分:マクロ/業種/個別`）を付けます。売買提案のアプリ（売買提案のアプリ）はこの記事を Chiezo から読みます。

**要約は Chidori では作りません。** 売買提案のアプリ の売買提案の AI が、参加者ごとにこの記事を読んで自分の売買のための要約を書き、Chiezo の収集 `pta_market` に溜めています。トップの「市況ニュース」の枠と、最新情報の市況ニュースのタブには、それを**書き手ごとに最新の 1 本ずつ**並べます（`Chidori.Topics` の `digest_from`。`Chidori.News.AiDigests`）。同じ記事から Chidori も 1 本書くと、AI に何が渡ったのかと人が読むものが別になるためです。トピックの網も育てません。

## トピック

記事から育った**話題の網**を図にします。一覧が 1 件ずつの索引、まとめがその期間の読み物だとすれば、こちらは**どの話題がどうつながっているか**です。**置き場所は `/news` の、まとめのすぐ下**です —— まとめが「この期間に何があったか」を文で言うのに対して、図は同じことを語のつながりで見せるので、別のページに置くと読む人が見に来ません。**出すのは持つ話題だけ**です（いまは一般ニュースと技術ニュース。記事が毎日まとまった数で流れてこないと、網になる前に語が古くなります）。

**語を拾うのは機械です。** 記事に付いたタグがそのままトピックになり、件数も一緒に出てくる語も Chiezo が数えます（`extract` の `of: "tags"`）。AI に語を思いつかせていた頃は、**記事に出てこない語が混ざり、同じ話題が回ごとに違う表記で増えました**。

**だから、記事のタグに固有名を書かせます**（製品・サービス・技術・組織の名前。集める回と整理の回のどちらにも頼んであります）。分野だけだと「AI」「セキュリティ」のような広い語ばかりになり、**どの記事も同じ場所に集まって図になりません**。配信元が 1 件ごとに付けている語（Qiita や Zenn のタグ）も Chiezo が材料として渡すので、書き手が付けた綴りをそのまま使えます。

**AI がやるのは精査だけです。** 言い換えを 1 つに畳む・親子を決める・技術の話でない語（媒体名や一般語）を外す・一言で説明する —— どれも数では決まりません。粒度が違うだけの語は畳ませず（畳むと片方が消えます）、**迷ったものは触らせません**（間違って外した語は二度と入りません。1 回見送るほうがずっと安い）。**Chidori は依頼文を渡して、できたものを読むだけ**です。

**溜め先は記事とは別の収集**（`<話題>_topics`。網羅）です。記事と同じ収集に置くと、流れの期限（30 日）でトピックまで消えます —— トピックは、増減はしても古いものが要らなくなるものではありません。

| 巡回 | やること | 間隔 |
|---|---|---|
| 機械収集 | 記事のタグを名簿にし、件数・直近の件数・一緒に出てくる語を数え直す。**AI を呼びません** | 1 時間 |
| 整理 | 手元の語を読んで、言い換えを畳み、親子と分野を決め、話題でない語を外す | 12 時間 |

**整理の回に渡すのは見出しとタグだけ**です（Chiezo の `{names}`）。本文まで見せると、語が増えるほど入り切らなくなり、しかも**切れるのは新しいほう** —— いちばん見てほしい「まだ精査していない語」が落ちます。**始めるのはその未精査のものから**で（`分野:` の付いていないもの）、1 回で終わらなくても次の回が続きから読みます。

**AI は自分でも Chiezo を引けます。** 収集の AI は Chiezo の MCP（`/mcp/knowledge`）に繋がっているので、渡した材料で足りなければ `search` / `doc` / `filter` で手元の知識を引いて確かめられます。**`query` で SQL も引けます** —— 同じ記事に一緒に付いたタグを数えられるので、つながりを思いつきで引かずに済みます。**読むだけ**です —— 短期記憶へ書く道具（remember / update / forget）は、この口には出していません（無人で回る回が書けると、人が覚えさせたものと機械が書いたものが同じ置き場で混ざるためです）。

**図の語彙は Chidori が持ちます**（関連図の画家と同じ形）。読む側と書かせる側が離れると静かにズレるためです。

| タグ | 意味 |
| --- | --- |
| `トピック` | この図に出す目印 |
| `分野:AI` | 色分け |
| `親:AI` | 上位のトピック（図ではその話題を真ん中にした囲みになる） |
| `同義:エージェント` | 畳んだ言い換え（図には出さない） |

数のほうは脇書きに入ります（**機械が毎回入れ替えます**）。`docs` / `docs_recent` がその語の付いた件数と直近の窓のぶん、`last_seen` が最後に付いた日、`links` が一緒に出てくる語（`語:回数`）です。

**話題は角丸の札で描き、札の大きさ（字の大きさ）は直近の件数です。** 丸にしていた頃は、入る字数が丸の大きさで決まって名前が切れ、大きさの差も 1.75 倍しかありませんでした —— 札なら名前を削らずに入れられ（長い名前だけ 2 行に折ります）、いちばん動いている話題は静かな話題の 3 倍の字で書きます。件数の合計だと、昔よく出てきた語がいつまでも大きいままになります —— 図で真っ先に読みたいのは「いま何が太いか」です。いちばん動いている語を基準にした割合で描くので、静かな日でも図は潰れません。**0 件になっても消さず、小さく描きます**（静かになったことも図から読めるように。いつまで動いていたかは一覧に出ます）。**線は一緒に出てきた回数**で、太さもその回数です —— AI に関連を書かせていた頃は、一度も一緒に出ていない組が線になっていました。

**全部の話題を置き、親子は囲み（クラスタ）で表します。** 親の札を最初に置き、子をそのまわりに詰めて、薄い角丸の枠で囲みます（孫も同じ形で入れ子になります）。**枠の左上には上位の話題の名前を書きます** —— 枠だけだと、何のまとまりなのかを中の札の大きさや位置から推し量ることになるためです。**操作は関連図と同じ**で、引きずって動かし、つまんで拡大します。**開いたときは、いちばん動いている話題を真ん中にして、名前が読める大きさで出します** —— そこから引きずって周りの話題を見に行きます（全部は「全体」のボタンで）。ほかのクラスタは、そのまわりへ動いている順に外へ詰めていきます。
- **線は全部出します**（網であることが見えないと、話題が箱に並んでいるだけに見えます）。数百本あるので薄く描き、**札を押すとその話題の線だけを濃く残し**、つながっていない札を薄くします（もう一度押すか、余白を押すと戻ります）
- **置き方は決まった手順で詰めるだけです**（力で散らしません）。開くたびに形が変わると「昨日と同じ図か」が読めなくなるためで、同じ材料なら同じ図になります。**札も囲みも長方形のまま詰めます** —— 囲む円で詰めると、横長の札の上下が空いて図が間延びしました
- **親が輪になっていても止まります**（AI が親子を逆にも書くことがあるので、たどって自分に戻る親は無いものとみなします）

**先の無い線は引きません。** 一緒に出てきた相手が、外された語や図の外のこともあるので、両端が図にあるものだけを線にします（一覧にはそのまま出します —— 黙って消すと、何が起きているのか読めません）。

**札を押すと、その話題の記事が図の下に並びます**（新しい順）。トピックは記事のタグの値そのものなので、Chiezo のタグの口（`filter?tag=`）で引きます。**トピックの語と、畳んだ言い換え（`同義:`）の両方で引きます** —— 記事の側は畳む前の表記のまま残っているので、語だけで引くと取りこぼします。子のトピックは含めません（広い語ほど件数が膨らむため。子へは図の上で移れます）。

### 興味トピック

**トピックの網から、興味のある語を選べます**（札を押して「☆ 興味トピックに入れる」。選んだ札は金色の縁になり、図の下に並びます）。選んだ語は話題ごとに Chidori の置き場（`chidori_data`）に持ち、収集へは依頼文に書き込んで送ります —— 何に興味があるかは利用者の都合で、Chiezo は題材も都合も持たない側だからです。

- **整理の回が、1 件ごとに興味度（0〜100）を付けます**（タグ `興味度:73`）。重要度とも話題度とも別の軸です —— あちらは「誰にとっても読む価値があるか」「界隈が話しているか」で、こちらは「この読者が選んだ語にどれだけ近いか」。記事一覧は「興味の近い順」にも並べ替えられます（点の無いものは後ろ）
- **興味トピックの要約を、ふつうの要約とは別に 1 本書かせます**（巡回「興味の要約」、タグ `興味のまとめ`）。ふつうの要約のすぐ下に出て、全画面で読めるのも同じです。**同じ依頼文で材料だけ絞ると、どちらも「その期間の総ざらい」になって読み分けられない**ので、依頼文を分けて「どの興味トピックの話か・何をすればよいか」を書かせます。まとめの時刻になると、ふつうの要約を知らせたあとに書かせて、**もう 1 通知らせます**（興味の要約で止まっても、ふつうの要約の結果は変えません）
- **選び直すと、整理と興味の要約の依頼文をその場で Chiezo へ送り直します。** 送るときは、いま Chiezo に入っている巡回ごとの相手をそのまま載せます（載せないと、画面で選んだ相手が既定へ戻ります）
- **付け終えた興味度は動かしません。** 興味トピックは選び直されますが、付けた点はその時点の興味での判断として残します（依頼文で「既に付いているものは付け直さない」と頼んであります）。整理の回が見るのは前回から入ったものだけなので、点が付くのは選んだあとに入る記事からです
- 選んでいなければ、興味度も興味の要約も作りません（付ける基準が無いのに数を書かせると、どの記事にも同じような点が並ぶだけになるため）
- **トピックは名前で探せます**（図の左上の検索欄。画家の図と同じ）。候補を選ぶと、その札へ寄って記事が開きます。全角半角・大文字小文字・カタカナとひらがな・中黒や空白の違いは同じ語として扱い、AI が畳んだ言い換えでも当たります

### まとめを ntfy で知らせます

**通知へ流すのは、レポート冒頭の要旨だけです。** 要旨は通知に流す前提で別に書かせています（**1 行目でその期間を一言、空行、要点を「・」で 3〜4 行**。記号の飾りなし）—— 全部を 1 つの段落に詰めると、通知でも画面でも読めません。通知は畳まれて先頭しか見えないことがあるので、**1 行目だけで意味が通るように**頼んであります—— レポートを潰して送ると、見出しも表も箇条書きも記号のまま並びます。同じ文が画面ではレポートの導入として出ます。**見出しは本文に写しません**（ntfy はタイトルを別に持つので、二度並びます）。**要点ごとに、根拠にした記事の出典を書かせ、通知では要点のすぐ下に `→ URL` で並べます**（どの URL がどの要点の根拠なのかが読めるように）。要点に出典の無い古いまとめは、出典の URL を末尾に 3 件まで添えます。

**画面と通知で、出典の出し方が逆です。** 画面では出典の URL を**記事の見出しでリンク**にします（裸の URL のままだと、押す前にどこへ行くのか読めません）。通知では **URL のまま**渡します —— ntfy が自分でリンクにするので、見出しに差し替えると行き先が読めないただの文字になります。

**時刻は Chidori が持ちます。** `/news` の「要約」の枠に「要約を作る時刻」を書くと（JST、`07:00,21:00` のようにカンマ区切り。空なら回りません）、その時刻に **整理を 1 回起こす → 要約を起こす → できたまとめを知らせる** まで Chidori が進めます。**Chiezo には「いま回してください」としか言いません** —— あちらは題材も都合も持たない側で、何時に読みたいかは利用者の都合だからです。

**時刻は「要約を作る時刻」で、通知はその後に付いてきます。** 話題の画面の「通知」の枠で「知らせる」にしてあれば作った後に知らせ、そうでなければ作るだけです（知らせない設定・通知先が無いのは失敗としては残しません）。通知の枠の中に時刻を置いていた頃は、通知の時刻に読めました。

**取り込みが混んでいても、その回を落としません。** Chiezo は取り込み中の依頼を積まずに断る（409）ので、断られたら空くのを待って頼み直します。待つのは**次の予定の時刻まで**で、それでも空かなければその回は諦めて理由を残します（画面から押したときは 1 時間まで）。**起こせたあとも、整理・要約それぞれ 30 分まで待ちます** —— Chiezo は収集を 1 本ずつ焼くので、ほかの収集が並んでいると起こした回が順番を待ちます（10 分・15 分で切っていた頃は、混んでいた朝に「時間内に終わりませんでした」で止まりました）。

**要約は時計を持ちません**（Chiezo 側では `on_demand` の巡回）。間隔で回していた頃は、回るたびに時刻がずれていくうえ、**いつ回ったかが分からないと知らせようがありません**。起こすのがこちらなら、できあがりを待って知らせられます。

**整理を先に起こすのは、整理されていないものでまとめさせないため**です（宣伝も重複もそのまま読み物に入ります）。起こした先は待ってくれない（Chiezo の口は「起こした」まで返す）ので、終わったかどうかは Chidori が読み直して確かめます —— 整理は収集の前回時刻が進んだか、まとめは見出しが変わったかで見ます。

**いまの状態と、前に走った回の記録は分けて出します。** 画面には「いまは動いています（次の定時の回は…）」と「前回の定時の回: …」が別の行で出ます —— 止まった回の理由は現在形で残るので（「Chiezo 側で止まっています」）、記録だと断らないと**ずっと前に止まった回の理由が、いまの状態として読まれます**（実際に読まれました。そのときは収集も要約も動いていました）。

**その場で作らせることもできます**（「いま作って知らせる」）。作り直さずに送るだけの「いまのまとめを知らせる」も残してあります。**押されたときは、知らせ済みでも送ります** —— 押すのは意思表示なので、そこで黙られると「壊れているのか、もう送ったのか」が分かりません（最後に知らせた時刻は画面に出ます）。

**通知を押すと、その話題の画面でいちばん新しいまとめを全画面で開きます**（`/news?view=<収集>&digest=latest`。端末への通知も同じ）。**ntfy では、開く先を外から開ける宛先があるときだけ添えます**（`PHX_HOST`）。手元しか指せないとき（既定の `localhost`）は添えません —— 通知を開くのはたいてい別の機械で、電話で押しても `localhost` は自分自身を指すので、開けないリンクが付くだけです（添えなければ、その通知は本文をそのまま扱えます）。

**同じ回は二度走らせません。** 走らせる前に予定の時刻を控えるので、数分かかる段取りの最中にその回がもう一度来ても起こしません。予定を逃したときは 30 分までなら走らせ、それより過ぎたものは追いかけません（夜中に立ち上げた拍子に朝の回が走らないように）。

**通知先（ntfy のトピック名と場所）は、設定画面の「通知」タブに全部の通知で 1 つだけ持ちます**（表 `ntfy_settings`）。話題の画面で決めるのは知らせるかどうかだけです —— 話題ごとに宛先を書いていた頃は、同じトピックを画面ごとに書き写していて、変えるときに全部を回る羽目になっていました。宛先は運用しながら変えるもの（試しに別のトピックへ流す、しばらく止める）なので、環境変数ではなく画面で決めます。**「ntfy に送る」を外せば、トピック名を残したまま ntfy へは送らなくなります**（登録した端末には送ります。トピックが空のときも送りません）。 既定の宛先は持ちません —— 公開の ntfy では、推測できる名前は誰でも読めるためです（推測されない名前にしてください）。

**ntfy の場所は、書かなければ公式の公開サーバー（`https://ntfy.sh`）へ送ります。** 自前で立てているなら `NTFY_BASE_URL` に既定を置くか、「通知」タブで上書きできます。場所まで空を「知らせない」の意思表示にしていた頃は、**宛先だけ書いた人のところに何も飛ばず、その理由は画面の隅にしか出ませんでした**（実際にそうなりました）。送るかどうかを決めるのは宛先のほうです。

**届かなかったものは知らせた扱いにしません** —— 記録すると、次からは黙って飛ばされ、そのまとめは永遠に届きません。

### 端末へ通知します（PWA）

ntfy と並べて、**ホーム画面に入れた Chidori（iPhone を含む）や、通知を許したブラウザへ直接知らせます**（Web Push）。両方あれば両方へ送り、**どちらか 1 つでも届けば知らせた扱い**です。話題ごとの「知らせる」はどちらにも効きます。

- **iPhone**: Safari の共有メニューから「ホーム画面に追加」→ ホーム画面の Chidori から開く → 設定の「通知」タブで「この端末で受け取る」（iOS 16.4 以降。https で開いているときだけ）
- **登録した端末は「通知」タブに並び**、外す・テスト通知を送るができます。受け取れなくなった端末（配信先が 404・410 を返したもの）は送ったときに外します
- **送り手の鍵（VAPID）は最初に要ったときに作って DB に置きます**（表 `web_push_keys`）。手で用意するものはありません。DB を作り直すと鍵が替わるので、端末は登録し直してください

記事本文は Chidori に保存せず、見出しを押すと Chiezo の中身（要約と出典）が開きます。

Chiezo 側で `CHIEZO_COLLECT_DIR` と `CHIEZO_NOTES_DIR` の両方が設定されている必要があります。

| 変数 | 既定 | 説明 |
| --- | --- | --- |
| `CHIEZO_BASE_URL` | なし | Chiezo のルートURL（Chidori から引く宛先）。未設定ならニュースも関連図もデータ収集も使えない |
| `CHIEZO_PUBLIC_URL` | `CHIEZO_BASE_URL` | 画面に置く Chiezo へのリンクの宛先（見る人のブラウザから開けるもの）。Chiezo をコンテナの名前でつないでいるときに書く |
| `CHIDORI_NEWS_COLLECTION` | `chidori_news` | 「一般ニュース」の話題が使う収集の名前。Chiezo のソース名になる（他の話題の収集名は定義が持つ） |
| `CHIDORI_NEWS_BACKEND` | なし | 収集を頼む相手（`claude` など）。**これは収集ぜんたいの下敷き**で、巡回ごとの相手は画面の表から選ぶ（巡回に書いてあればそちらが勝つ）。未設定なら Chiezo の既定にまかせる |
| `CHIDORI_NEWS_MODEL` | なし | その相手のモデル |
| `CHIDORI_NEWS_EFFORT` | なし | その相手の考える量 |
| `DATABASE_URL` | なし | PostgreSQL の接続先。本番では必須 |
| `CHIDORI_PAINTERS_COLLECTION` | `chidori_painters` | 画家の図を溜める Chiezo の収集の名前 |
| `CHIDORI_BOOK_POSTS_COLLECTION` | `chidori_book_posts` | 「技術書を勧めている記事」を溜める Chiezo の収集の名前 |
| `CHIDORI_BOOKS_COLLECTION` | `chidori_books` | 「本棚（定番の技術書）」を溜める Chiezo の収集の名前 |
| `CHIDORI_PIHOLE_COLLECTION` | `chidori_pihole` | 「Pi-hole の通信」を溜める Chiezo の収集の名前 |
| `NTFY_BASE_URL` | `https://ntfy.sh` | ntfy のルートURL の既定。**通知先（トピック）は設定の「通知」タブで決める**（空なら知らせない） |

誰に頼むかは本来 Chiezo 側の判断なので、名指しするのは「この収集だけは別の相手に」と決めたときだけです。依頼した後は Chiezo の管理画面からも変えられ、画面には Chiezo が持っている値を出します。

## データ収集

`/datasets` では、**他のアプリで使うデータ**を Chiezo に集めさせる依頼を出します。関連図や最新情報と違い、**この画面は溜まったものを見せません** —— 読むのは使う側のアプリで、こちらが持つのは依頼と進み具合だけです。同じものを 2 つの画面に出すと、どちらが本当の状態なのか読めなくなります。**例外は読む側のアプリを持たない対象**で、技術書の本棚と Pi-hole のドメインはこの画面に並べます。

**集めるものごとにタブで分かれています**（いまは「技術書」「Pi-hole」と、食事処の範囲ごとのタブ）。定義は `Chidori.Datasets.defined/0` にあります —— 足すときはそこへ 1 つ書けば、タブも依頼も増えます。

### 定番の技術書

**「良い本」ではなく「勧められている数」で決めます。** 1 人が絶賛した本と、何十本の記事が挙げてきた本は別物で、後者が「技術者なら読んでいる」に当たります。

**そのために、本ではなく記事を溜めます。** AI にその場で探させて数えさせると、**同じ本が次の回では見つからず、数が増えたり戻ったり**します —— 記事のほうを溜めておけば、同じ材料からは同じ数が出ます。収集は親子の 2 つです。

| 収集 | 何が溜まるか | 誰が |
|---|---|---|
| `chidori_book_posts` | 技術書を勧めている・参考文献に挙げている記事 | 機械収集（はてなの検索 RSS。**巡回の相手が検索文を考えてから引く**）／ 整理（AI が**まだ読んでいない記事だけ**を開いて「本:<書名>」のタグを付ける） |
| `chidori_books` | 本棚（1 冊 1 文書） | 機械収集（タグを数えるだけ）／ 整理（AI が全冊の書名を見て言い換えを畳み・技術書でない語と本（小説・漫画・古典など）を外し、**まだ調べていない本だけ**に分野・話題・説明・ISBN を付ける） |

**検索文は回ごとに AI が考えます。** 同じ検索文で引き直しても同じ記事が返るだけなので（実測で 1 回目 158 件、2 回目は全部が既にあるもの）、機械収集の回は Chiezo の時計で回るたびに、① 前の回の検索文ごとに入った記事の数と、消されずに残った数を数える（記事に付く「検索:<検索文>」の印で）、② これまでの検索文と数をその巡回の相手に見せて、まだ試していない切り口の検索文を考えさせる、③ その検索文で配信元を展開して引く、を進めます。**考えるのも控えるのも Chiezo** です（配信元の URL の `{query}` と、巡回の依頼文の `{queries}`）。考える相手は技術書のタブの巡回の表で選べ、控えは Chiezo の管理画面の収集の面で見られて消せます。1 回目は最初の組の検索文をそのまま使います。使った検索文は 60 日のあいだ使わず、それを過ぎればまた使えます（記事は増えていくため）。**探すのは記事の見出しだけ**です（はてなの `target=title`。本文検索では語をどこかに含む記事をゆるく拾い、入った 163 件のうち本を勧めていたのは 5 件でした）。検索文 1 つにつき人気順を 3 ページ、新着順を 1 ページ引きます（人気順で過去の定番の記事を、新着順でこれからの記事を拾う。定番の推薦記事は人気順の 2〜3 ページ目に多く、1 ページ目だけでは本がほとんど重ならなかった）。

**数は機械が数えます。** その本のタグが付いている記事の数が、そのまま「何本の記事が勧めているか」です。**AI は数に触りません** —— 畳む・分野を付ける・説明する、だけが AI の仕事です（トピックの網とまったく同じ形）。

**調べ終えたものは調べ直しません。** 整理の回に渡すのは、Chiezo が「まだ AI が目を通していない」印を付けているものだけです（差し込み口 `{unreviewed}`）。渡したものは、調べがついてもつかなくても印が外れるので、読めなかった記事や ISBN の見つからない本を毎回やり直すことはありません。1 回の整理に渡すのは勧めている記事の多い本から 20 冊までで（数は Chiezo が決め、AI には渡した本を全部調べさせる）、残りは次の回に回ります。依頼文を直して調べ直させたいときは、Chiezo の収集の画面の「全部を未確認に戻す」で初めから回し直せます。1 冊だけなら、本を押して開く詳細の「この本を Chiezo に調べ直してもらう」から、本棚の整理の回にその本だけを確かめ直させられます（書き添えたことは補足として渡ります）。

**技術書のタブの頭に本棚を並べます**（おすすめ度 = 勧めている記事の本数の高い順）。表紙は ISBN から[版元ドットコム](https://www.hanmoto.com/)の書影を出します（ISBN が分かっていない本は表紙の枠だけ）。本を押すと詳細が開き、勧めている記事の一覧と、その本の調べ直しを頼む欄が出ます。本には技術ニュースのトピックの名前で「話題:」のタグが付き、**技術ニュースで選んだ興味トピック（その言い換えとすぐ下の子を含む）に当たる本を強調します**（絞り込みもできます）。

**読んだ本には印を付けられます**（本の詳細の「読んだ記録」。読んだか・読んだ日・メモ。関連図の「見た記録」と同じ形）。印は Chidori の置き場（`chidori_data`）に残し（本棚の収集には書きません）、本棚の一覧では「読んだ」の札を付けて薄く出します。**「オライリー以外の未読の上位 10 冊」と「オライリーの未読の上位 10 冊」からは外します**（技術書の画面とトップページ）—— あの枠は次に何を読むかを決めるためのもので、読み終えた本が並び続けると、まだ読んでいない本が押し出されるためです。

### Pi-hole の通信

家の LAN の Pi-hole が**止めたドメイン**と、**いつもと違う振る舞いの通信**（はじめて見た・存在しない名前が返り続ける・珍しい種別・規則正しい周期・毎回ちがう長い名前）を、**ドメインごとの集計として積み上げ**、何のドメインか・放置してよいかを AI に web で調べさせます。

| 収集 | 何が溜まるか | 誰が |
|---|---|---|
| `chidori_pihole` | 1 ドメイン 1 文書 | 機械収集（**Chiezo が Pi-hole から新しい問い合わせだけを読み**、最初と最後に見た時刻・問い合わせと止めた回数・アクセス元ごとの回数を前の回に足す。1 時間おき・AI は呼ばない）／ 整理（AI が**まだ調べていないドメインだけ**を、気になる通信を先に 10 件ずつ web で調べ、本文に「ひとことでいうと・何のドメインか・どの製品が使うか・通信から言えること・放置してよいか」を書き、判定「問題なし・要注意・不明」を付ける） |

**Pi-hole に繋ぐのは Chiezo です**（巡回「Pi-hole から引く」と、いま止めている通信の読み口 `GET /v1/pihole/blocked`）。接続先とパスワードは Chiezo の管理画面の「API キー」の面で `pihole_url` と `pihole_password` に登録します。Chidori は Pi-hole に直接つながりません。**溜めるのは止めたものと気になる通信だけ**で、一度溜めたドメインは、また出てくるたびに集計が足されます。いまの状態（止めているか・気になる通信か）は集計の側で読みます（タグは最初に溜めたときにしか付かないため）。

**いま止めている通信を流せます**（タブの頭の「流す」。Pi-hole の監視アプリ の「1件ずつ流す」と同じもの）。押した時点から先に Pi-hole が止めた問い合わせを、5 秒ごとに Chiezo 越しに読み、新しいものを上に 1 件 1 行で足します（500 行まで。同じドメインでも来るたびに 1 行）。溜めているドメインは押すと詳細が開きます。

**タブの頭にドメインの一覧を並べます**（気になる通信を先に、止めた回数の多い順。「気になる通信」「止めたもの」「要注意」で絞れます）。調べたものは「ひとことでいうと」を一覧に出し、押すと集計（最初と最後に見た時刻・回数・アクセス元ごとの回数）と調べた中身の全文が開きます。

**ドメインには「見た」印とメモを付けられます**（詳細の「見た記録」。見たか・見た日・メモ。関連図の「見た記録」と同じ形で、同じ置き場 `chidori_data` に種類 `pihole` で持ちます。収集には書きません）。一覧では「見た」の札を付けて薄く出し、「まだ見ていない」で絞れます（Pi-hole の監視アプリ の「確認済み」に当たるもの）。

### 食事処（travel-log 向け）

travel-log の地図に並べる「食べに行く先」を、**決めた範囲の中だけ**集めます。**網羅の収集**なので、期限で古いものを落とすことはしません（落とすと地図に穴が開きます）。**AI の回には、隣の区画にある店も見せます**（Chiezo の `{nearby}`。区画を 200m 広げた範囲にある、区画の外の店の見出しと座標）—— 区画の中しか見せないと、密集した地区では境目の向こうに既にある店を「足りない」と読んで足し直し、被りが大量に出ていました。

**範囲ごとに収集が 1 つです**（`Chidori.Datasets.DiningAreas`。収集の名前は `chidori_dining_<番号>`。番号は空いているいちばん小さいもので、Chiezo に同じ名前の収集が残っている番号は使いません —— 範囲を外しても Chiezo の収集は消さないので、使うと前の範囲の店を引き継ぐためです）。日本全体を 1 つの収集で回していた頃は、59.7 万件・4,105 区画で一周のめどが立たず、AI の費用もかさみ、抜け漏れと間違いが多すぎて地図として使えませんでした。

- **範囲は `/datasets/areas`（データ収集のタブの端の「＋ 食事処の範囲」）で、地図に四角を描いて足します。** 地名で探して寄り、「四角を描く」を押してドラッグします（探した場所のまわり 3 km ほどで作ることも、南北東西を数で直すこともできます）。全体は手元の白地図で、寄ると[地理院タイル](https://maps.gsi.go.jp/development/ichiran.html)（国土地理院の標準地図）に切り替わり、駅や道まで見えます（タイルは見ている人のブラウザが国土地理院から取ります。参照元は送りません）。四角を決めると、中にある飲食店の数（辞典ごと）と区画の見込みをその場で出します。広さは縦横とも 0.5 度まで
- **離れた場所は別の範囲にします** —— 1 つの四角で囲むと、あいだの見たくない土地まで AI が回ります
- **travel-log からの依頼は、範囲の画面でまとめて受けられます**（「travel-log からの依頼」）。travel-log はいくつもの範囲を 1 つの画面で扱うので、依頼のテキストにはどの範囲の店かが書いていません —— 貼ると 1 件ずつ座標の入る範囲（重なっていれば狭いほう）へ控え、位置OK・位置修正はその範囲の収集で固定させます（位置修正は店が今いる座標で振り分けます）。どの範囲にも入らない依頼は控えずに画面に出します。頼むのはこれまでどおり範囲のタブの「控えている依頼」から。範囲の一覧に控えている件数が出ます
- **全範囲を 1 つの ZIP に書き出せます**（範囲の画面の「全範囲をまとめて書き出す」。`/datasets/areas/travel-log.zip`）。travel-log では範囲によらず 1 つの種別（`dining`）に読み込むので、範囲ごとに読み込ませずに済みます。範囲が重なったところで同じ店（同じ名前で 30m 以内）が 2 つの範囲に居るときは、先に作った範囲のほうだけを入れ、もう片方は exclude.txt に回します
- **名簿は 3 つの辞典を範囲の四角で絞って引きます**（Chiezo の抽出の `bbox`）。区画も範囲の四角を割り、**1 区画 20 件の目安**です。AI が 1 回で 1 件ずつ確かめられる数にしてあります —— 1 区画 150 件で回していた頃は、AI は 1 区画を 90〜135 秒で見ていて（1 件 1 秒に満たない）、閉店や実在を確かめる見方になっていませんでした
- **範囲の収集は、それぞれ独立した収集です**（ほかの収集からは引き継ぎません。名簿は 3 つの辞典だけから引きます）
- **作ったら、その範囲のタブで「収集の設定を更新」を押すと Chiezo に収集ができます**（止まった状態で作られます）。範囲を外しても Chiezo の収集は消えません
- **作った範囲は地図に名前の札つきで出て、あとから直せます**（札か一覧の「範囲を直す」）。四角を変えて保存すると、Chiezo の収集へ範囲で決まるところ（説明・名簿の指定・区画）だけを送り、**機械収集から走らせ直します**（広げたぶんの店を名簿に入れるため。巡回は送らないので、選んだ相手は変わりません）。区画は次の回に新しい範囲で割り直されます。前の範囲で見終わった区画の印は残るので、広げたところだけをざっと見るが見に行きます（一周して止まっていても、そこだけ動き出します）。外した場所の店は travel-log へ書き出さず、前に読み込んだぶんは exclude.txt で消します

**名前と座標は AI に書かせません。** 名簿は Chiezo の 3 つの辞典から機械的に引きます —— 座標を書かせると当てにならない値が混ざり、しかも実行のたびに違う値になります。AI に頼むのは、そこに書いていないことだけです（まだ開いているか・食べに行く先か・どう紹介するか）。

**ひとつの辞典では要る項目が揃いません。** 同じ店が複数の辞典に居たときに、どの項目をどこから採るかまで決めてあります。

| 辞典 | 件数 | 勝つ項目 | なぜ |
|---|---|---|---|
| 百科事典（`jawiki`） | 約 900 | 説明・出典 | 読み物になる紹介文があるのはここだけ |
| 地図辞典（`osm_japan`） | 約 10 万 | 座標・住所・サイト | 現地を歩いた人が置いた点で、いちばん確か |
| 店舗辞典（`overture_japan`） | 約 41 万 | （何も勝たない） | 件数はいちばん多いが、値の確かさは上の 2 つに劣る |

**順位を譲ることと、その値を捨てることは別です。** 百科事典は座標で勝ちませんが、地図に載っていない 1 軒の座標はそこにしか無い —— 捨てると、**その 1 軒はどの区画にも入らず、AI から永遠に見えなくなります**（区画は座標で決まるため）。Chiezo は勝った辞典で埋めたあと、空いたところを残りの辞典で埋めます。

**どの辞典も絞りません。** 網羅の収集なので、機械で引けるものを取りこぼすと、そのぶんを巡回が区画ごとに探し直すことになります —— **機械で済む仕事を AI に払わせる**形です。地図辞典にはもう一段の理由があり、あちらは飲食店にどれも同じ点しか付けないので、件数を書くと並びが見出し順になり、名前が先に来るものだけが残ります（数字と英字の名前が入って、仮名の途中で切れる）。

**一周の長さは、区画の大きさではなく件数で決まります。** AI は 1 件あたり約 1.1 秒（実測）で、Chiezo は区画ごとに 1 回ずつ直列に聞きます。**区画を大きくしても一周は縮みません**（同じ店を同じだけ読ませるので）。減るのは 1 回ごとの定型文の無駄だけです。

**一周にかかる日数は、こちらでは決め打ちしません。** 巡回に書くのは「これくらいで一周したい」という希望で、実際の速さは**区画の数**と**Chiezo が 1 回に見る区画の上限**で決まります —— 区画が増えれば伸びますし、上限に当たれば書いた日数には届きません。**いま何日かかるかは Chiezo の画面**（収集の面の巡回の表）で読んでください。

**1 区画の大きさは、入り口ではなく出口で決めています。** この回は残す店ぜんぶにタグと紹介文を付けさせるので、区画の件数がそのまま AI の返す件数になります。実測では **150 件が切れずに全部返り**、47,685 文字・2 分 50 秒でした（1 件あたり約 318 文字）。切れると、返らなかった店は中身が空のまま次の一周まで残ります。いまは 1 件ずつ確かめさせるために 20 件まで小さくしてあります。

**同じ店が 2 つに分かれることがあります。** 畳めるのは見出しがそのまま一致したときだけで、実測では、同じ範囲の地図辞典と店舗辞典で名前が一致するのは 3%（60m 以内という条件を足しても 2〜9%）。**畳めなかったぶんは別の 1 件として並びます** —— 気づけるのは区画をまとめて見る AI の回のほうなので、そちらに「1 つにまとめてください」と頼んであります。どちらの値を残すかは 1 件ごとに付いた出典のタグで決めます（座標は `出典:OSM`、説明は `出典:Wikipedia`）。一方、**百科事典の見出しは辞典とよく一致します**（東京都の飲食店 128 件のうち地図辞典に 47 件・店舗辞典に 72 件）。紹介文が要るのはまさにそこなので、この形がいちばん効きます。

**区画は座標で割ります**（店の多いところは細かく、少ないところは粗く）。母集団は集めたもの自身で、対象の矩形には範囲の四角を書いてあります。

- 母集団を自分自身にするのは、**そのときだけ Chiezo が区画を割り直す**ためです。座標が直れば区画もそれに追随します。
- 矩形を書くのは、**まだ 1 軒も入っていない範囲を対象から落とさない**ためです。点から矩形を作ると点の無いところは矩形の外になり、「ここに足りない店はないか」を永遠に問えません。

| 巡回 | やること | AI |
|---|---|---|
| 名簿 | 3 つの辞典から機械的に引く（一度きり・足すだけ。範囲を直したときは走らせ直す） | 使わない（相手も選べません） |
| ざっと見る | 区画ごとに、**並んでいる店を 1 件ずつ確かめ**（営業しているか・食べに行く先か・座標・重複・空欄）、そのあと**足りない店を足す**。**一周したら止まる** | Chiezo の AI（2 時間ごと・一周 3 日の希望） |
| 整理 | ざっと見るが一周したあと**ゆっくり回り続ける**。travel-log からの報告 → まだ目を通していない店 → 足りない店を足す、の順で、残りの時間で並んでいる店（とくに閉店）を見直す | Chiezo の AI（12 時間ごと・一周 14 日の希望） |

**どちらも名簿ができてから走ります。** 名簿が無ければ区画には何も並ばず、空の一覧に向かって「この範囲の全部です」と言うことになります。

**ざっと見るで全件を一度ずつ確かめ、整理はそのあとの手入れをします。** 名簿を引いた直後は閉店・重複・空欄が溜まっているので早めに一周し、そのあとは AI の枠を節約するためにゆっくり回します（整理を自動で回したくなければ、設定ページで止められます）。整理は一度見た店を毎回確かめ直さず、まだ目を通していない店と足りない店を先にします。その次に、埋まっていない情報がある店（とくに営業日と営業時間。無いと朝食営業・ランチ営業の絞り込みにかからない）を調べて埋めさせます。ただ閉店の取りこぼしは多いので、残りの時間で見直しも続けます（見直せなかった店は `not_reviewed` で申告させない —— 申告すると区画が毎回先頭に戻ってくる）。足りない店は口コミサイトや地図サービスで区画の町名・丁目の一覧を引いて突き合わせ、閉店は店ごとの頁の「閉店」「移転」の表示で見るよう、探し方まで書いてあります。**何を調べたかは答えの `checked` に 1 行ずつ残させます**（地図には載らない。Chiezo の AI の履歴の全文で読める）。travel-log からの報告が付いた回も、答えたあとはこの仕事を続けさせます。区画は 20 件なので、1 回で 1 件ずつ web で営業を確かめたうえで足りない店も探せます。時間が足りなければ確かめるほうを優先させ、確かめきれなかった店は `not_reviewed` で申告させます（次の回にもう一度渡る）。

**割り込み（「この区画を先に調べて」「この店が違う」）は整理が引き受けます** —— 人が待っている場面なので、その場で聞ける回でないと意味がありません。

**travel-log から届いた依頼は、その場所を含む区画の整理として頼みます**（「Chiezo の収集」の下の「travel-log からの依頼」）。travel-log の管理画面の「修正・追加の依頼」の「渡すテキスト」をそのまま貼ると、**すぐには頼まず 1 件ずつ控えます**（表 `pending_requests`。同じ依頼を貼り直しても 1 件のまま）。控えは座標で持ち、見るたびにいまの区画へ振り分けて、**区画ごとに件数の多い順**に並べます（区画を割り直しても迷子にならない）。**地図や一覧で区画を選ぶと、その区画に控えている依頼も出ます**（そこから「この区画を頼む」「控えを捨てる」も押せます）。「この区画を頼む」を押すと、**その区画で整理を 1 回走らせて、溜まった依頼を依頼文の補足として載せます**（整理を自動で回さないようにしていても、名指しなので走ります）。貼ったその場で頼んでいた頃は、1 件しか依頼の無い区画にも AI の回が 1 回ずつ走り、枠を使い潰していました。Chiezo が受けたら控えから消え、断られたら残ります（Chiezo の `once.notes`。保存はされないので、定時の回は元の依頼文のまま）。**「[位置確認]」の行（travel-log の「位置OK」）と「[位置修正]」の行（ピンを動かして指した位置）は AI に渡しません** —— 頼むだけでは守れないので、座標の近くの同じ名前の店を Chiezo から引き、その座標を固定させます（Chiezo の locks。次に焼くときから、AI の回が動かしても名簿を引き直しても戻り、「座標確認済み」のタグが付く。依頼文でもそのタグの店の座標は直さないよう頼んでいる。travel-log へ書き出すとカテゴリ「位置確認済み」になるので、取り込み直せば Chiezo まで届いたか分かる。固定されていない店は「位置未確認」で、現地で確かめて回る店を絞り込める）。**位置を固定した店は、AI が閉店と読んでも消えません** —— Chiezo が墓標を「閉店の可能性あり」のタグに置き換えて残し（収集の `locked_doubt_tag`。理由は脇書きの `doubt_reason`）、travel-log ではカテゴリ「閉店の可能性あり」になるので、現地で確かめ直せます。**人が travel-log から「閉店している」と報告した店は、頼む直前に固定を外します**（`Requests.release_closed/2`。理由に閉店・廃業・なくなっていた などが書かれた `[修正]` の行）—— 外さないと、現地で見た報告まで「閉店の可能性あり」が付くだけで残ります。位置修正はいまの座標で店を探し、動かした先の座標で固定させます。近くに見つからなかった店は画面に出します。固定は次に焼くときから効くので、**「AI を使わずにいま反映する」**で名簿を引く回（機械収集。AI を呼ばない）を 1 回走らせると、AI の回を待たずに反映されます。**依頼の頭には前置きを付けます**（`Requests.preface/0`）—— 現地で見た人の報告なので、足りない店を探すより先に答えさせ、「閉店」「無い」は営業中だと確かめられない限り消させます（小さな店の閉店は web に出ないので、「確かめられなかった」を残す理由にさせない）。「ある」「〜に変わった」と報告された店は、web で見つからなくても報告の名前で足させます（変わった報告は前の店を消すのと組で。一字違いなら web の名前に寄せる）。

- **割り込みではなく、ふつうの回として走らせます** —— 割り込みは「書かれたものだけを直す」回で、足りない店を探しに行く仕事に向きません。区画には印が付きます
- **区画は座標で引きます** —— 追加の依頼は名前を持たないので、場所は座標でしか言えません。同じ区画に入る依頼は 1 つにまとめ、**どの区画にも入らなかった座標は画面に出します**（黙って落とすと、その依頼だけが誰にも読まれない）
- **補足は区画ごとに分けて渡します** —— Chiezo は区画ごとに AI を呼び、見せるのはその区画の中身だけです。全部の区画に同じ依頼を渡すと、その店を見ていない AI まで答えようとして、中身を知らないまま書き換えることがあります。1 行ずつ座標で振り分け、見出しの行はどの区画にも、座標の無い行は直前の依頼と同じ区画に付けます
- **1 回に頼めるのは 20 区画まで**（Chiezo の天井）。超えたら切らずに断ります
- **取り込み中なら最長 1 時間、空くのを待って頼みます。** 待つのは Chidori の中なので、画面を閉じても頼み続けます
- travel-log が読む収集では、この欄が「いま頼む（割り込み）」の代わりになります
- **依頼と、その結果を並べて出します**（「依頼の結果」。新しい 5 件）。頼んだ時刻・区画・依頼のテキストを Chidori が控え（`dataset_requests`）、Chiezo の変更履歴（`/v1/collect/changes`）から**頼んだ後に、頼んだ区画をちょうど見た回**を結果として引き当てます —— 変更履歴には、その回がどの依頼から走ったのかが残らないためです（定時の回は Chiezo が選んだ区画を見るので、区画の組がそっくり一致することはまずありません）。足した・直した・消したの件数と見出しを色分けして並べ、**見出しを押すと Chiezo の画面でその 1 件の「直す前との違い」が開きます**。Chiezo の控えは見出しの頭のほうだけなので、出しきれないぶんは「ほか N 件」と出します
- **最近の回も並べます**（「最近の回」。新しい 10 回）。依頼の結果は依頼ごとに回を引き当てるので、**自動で回った回**（ざっと見る・整理・機械収集）は出てきません —— こちらは Chiezo の変更履歴をそのまま新しい順に並べ、足した・直した・消した見出しを同じ形で出します。依頼で走った回には「依頼」の印を付けます

**集めるのはイートインできる店だけです。** 持ち帰り専門の弁当・惣菜・菓子の店、百貨店の地下や駅ナカの物販売場は、地図に並べても行き先にならないので外させます（**持ち帰りもやっている店は残します** —— 寿司屋や麺類の店の持ち帰りは、その店の一部です）。

**座標のずれは、消す理由にしません。** 直させるのは座標のほうです —— 「本来の区画へ移す」つもりで消されると、移った先の回はその店を知りませんし、消したものに立つ墓標が名簿からの復帰も止めるので、**そこで消えたまま**になります（実際に 2 件起きました）。依頼文でそう書き切ってあります。

**押す口は「Chiezo の収集」の枠にある 1 つだけ**です（関連図・最新情報と同じ形）。収集がまだ無ければ**止まった状態で**作り、あれば Chidori が持っている抽出の指定・依頼文・区画の割り方・巡回を送り直します。**走らせはしません**。区画の一覧から「先に調べる」を押すと、その区画だけを先に見てもらえます（定時の巡回の進み具合にも次の予定にも触りません）。

**区画は地図にもなります。** 「8,185 区画のうち 2 つ見終わり」と数で言われても、**それがどこなのかは読めません** —— 四角を並べて、見終わったところを緑で出します（薄い緑が片方、濃い緑が 2 本とも見終わったぶん）。**進み具合は巡回をまとめて測ります** —— 1 本だけを見ると、もう片方が回っているのに「まだ」のままになります。

- **白地図は手元に持ちます**（`priv/geo/japan_coast.json`。Natural Earth のパブリックドメインのデータを日本の範囲で切り、0.012 度で間引いたもの）。全体はこれだけで描きます。**寄ると[地理院タイル](https://maps.gsi.go.jp/development/ichiran.html)（国土地理院の標準地図）を下に敷き**、区画を薄く塗って透かします —— 範囲の収集は区や駅の細かさなので、白地図だけではどの区画がどこなのか読めません（タイルは見ている人のブラウザが国土地理院から取ります。参照元は送りません。範囲の画面と同じ `assets/js/gsi_tiles.js`）
- **操作は関連図と同じ**です（`assets/js/pan_zoom.js`。「関連図」の「図の操作」）。**開いたときは全体が見える倍率**から始まります
- **濃さは詰まり具合の順位**（広さあたりの件数の順）。区画は矩形を端から端まで覆うので海の上にも載ります —— 同じ濃さで塗ると全面が埋まり、島の形が沈みます。**値の比では塗れません** —— いちばん詰まった区画と外海の区画は 5 億倍離れていて、上位 1 割を基準にしても中央値が 0.14 まで落ちます
- **大きさは細くても本当のまま**です。見える太さまで太らせていた頃は 8,185 区画のうち 6,295 が下限に当たっていて、**寄っても本当の大きさに戻りませんでした**。足りないぶんは**画面 1px の縁**で補います（寄ると相対的に細くなるので、嘘が残りません）。**400 倍まで寄れて**、寄ると区画の境目が出ます —— いちばん細い区画は図の 0.009 なので、12 倍では 1px に届きません
- **角は端の座標を丸めて出します**（幅ではなく）。幅を別々に丸めると隣と端が合わず、**白い筋**になって出ます（実測で 6,127 区画）
- **並べ方はメルカトル。** 緯度をそのまま縦に使うと北へ行くほど横に潰れ、九州と北海道で形が変わって見えます
- **押しただけでは走りません。** 件数と「見終わったか」を読んでから頼めるよう、選ぶのと頼むのを分けてあります

**溜まったものは travel-log が読みます。** 1 店 1 文書で、タグ `食事処` で拾えます。**書き出しは範囲ごとの ZIP ですが、読み込み先は 1 つの種別（`dining`）です**。travel-log の取り込みは key ごとに足すか上書きするだけなので、範囲の ZIP を順に読み込めば同じ種別に並びます。**スポットの key には範囲の番号を付けます**（`3-1234`。`doc_id` は収集ごとに 1 から振られるので、付けないと範囲どうしで key がぶつかり、あとから読み込んだ範囲が前の範囲を上書きする）。**シリーズの並びと色は Chidori の語彙の順に固定します**（`settings.json` は読み込むたびに種別の設定を上書きするので、ZIP に入っている店から作ると、範囲を読み込むたびに並びも色も入れ替わり、前の範囲にしか無いジャンルが一覧から落ちる）。**travel-log で付けたシリーズの見た目（アイコン・色）は残してもらいます**（`settings.json` の `keep_series_styles`。足されるのはまだ無かったジャンルだけ）。

| travel-log の項目 | 収集の中身 | 誰が入れるか |
| --- | --- | --- |
| 名前 | 見出し | 辞典（同じ見出しは 1 件に畳まれる） |
| 座標 | `extra.lat` / `extra.lon` | 地図辞典が優先（食い違うものだけ AI が直す） |
| 地域 | タグ `地域:<都道府県>` / `extra.area` | 百科事典のカテゴリと地図辞典（無いものを AI が足す） |
| シリーズ | タグ `ジャンル:…` の先頭 | 辞典のカテゴリ（抜けているものを AI が足す） |
| カテゴリ（絞り込み） | タグ `特徴:…`（朝食営業・ランチ営業・深夜営業・ゆっくりできる・1人で入りやすい・個室あり・子連れ歓迎・予約がおすすめ）と `extra.opening_hours` | 営業時間を持つ店は朝食営業（朝 8 時に開いている）・ランチ営業・深夜営業を機械で、残りは AI が確かめられたものだけ |
| ランク | タグ `ランク:A〜E`（**地図の丸の大きさ**） | AI（`extra.pageviews_month` が目安） |
| 説明 | 本文の 2 行目以降 | 百科事典が優先、無ければ AI |
| 連絡先・公式サイト | `extra.phone` / `extra.website` | 地図辞典が優先 |
| 出典の URL | `extra.url` | 百科事典の記事、無ければ AI（開いてその店の頁だと確かめたものだけ） |
| 営業日・営業時間（説明に添える） | `extra.opening_hours` | 地図辞典（持っているのは地図辞典の飲食店の 1 割ほど）と、ざっと見る・整理の回の AI（営業を確かめた頁に載っていた店だけ。OSM の `opening_hours` の書き方で、ここから朝食営業・ランチ営業・深夜営業の印が機械で付く）。**travel-log の説明には日本語に直して添える**（`月〜金 11:00〜14:30 / 定休日: 水`。知らない書き方が混ざっていれば元のまま） |
| （どの辞典から来たか） | タグ `出典:Wikipedia` / `出典:OSM` / `出典:Overture` | 機械（複数に居た店には複数付く） |

**説明に添える URL は Chiezo に確かめさせます**（収集の `links`。`Chidori.Datasets.ShopLinks`）。AI が口コミサイトの店の番号を推し量って書いた URL は別の店の頁になり、地図辞典の公式サイト欄にはドメインごと無くなったものが残るためです。書き出すときに、開けなかった URL と、題名に店の名前が無い口コミサイトの頁を落とします（公式サイトは題名を問いません。断られただけのものと、まだ確かめていないものは今までどおり書きます）。http から同じホストの https へ転送されるものは https で書きます。

**閉店したものは墓標で消します**（Chiezo が消えた扱いにするタグ）。辞典は閉店をすぐには落とさないので、ここは AI にしか見分けられないところです。消す理由を本文に書かせているのは、消したものは名前が並ぶだけで、理由が無いと消し間違いに気づけないためです。AI が目を通したあとで消えたもの（= 前に書き出したことがあるもの）の key は travel-log 用の ZIP の `exclude.txt` に入り、travel-log で読み込むと、前の回に入ったぶんも消えます。どちらなのかは Chiezo が消した時点で残す印（`extra.removed_after_review`）で見分けるので、印を残すようになる前に消えたものは入りません。

**閉店した店が戻ってこないようにしてあります。**

- **辞典の地物は元の id で見分けます**（抽出の指定の `identity`。OSM は `osm_type` と `osm_id`、Overture は `overture_id`）。同じ名前の店の見出しの札は辞典を取り込み直すと付け直されることがあり、見出しだけで見分けていると、消した店が新しい見出しで名簿の回から戻ってきます。
- **ざっと見る・整理の回には、足す前に営業しているかを確かめさせます**（閉店した店の記事や口コミの頁は何年も残るため）。

## 利用者が書いたことの置き場

**興味トピックと、読んだ・見た記録（技術書・関連図・Pi-hole のドメイン）は、Chidori の DB ではなく Chiezo の名前付きの置き場 `chidori_data` に預けます**（`Chidori.DataStore`）。動かす場所を変えたり DB を作り直したりしても消えず、同じ Chiezo を見ている Chidori どうしで共有できます。置き場は無ければ起動時に作ります。1 件 1 文書で、タグ `興味トピック` / `見た・読んだ` で分け、中身は脇書き（extra）に持ちます。

起動時に全部を読んで手元に持ち、書くときは Chiezo に書いてから手元を直します。Chiezo に届かない間は空として扱い、書くのは断ります（30 秒おきに読み直す）。
それ以外の設定（トップの並び・通知・控えている依頼など）は、その Chidori ごとのものなので DB に持ちます。巡回の間隔・整理を止める収集・知名度の下限は、設定の「Chiezo 収集」の「Chiezo から戻す」で、食事処の範囲は範囲の画面で、Chiezo の収集から戻せます。

## 起動

`docker compose` で PostgreSQL ごと立てる。開発サーバーは `http://localhost:7000`。

```bash
cp .env.example .env   # SECRET_KEY_BASE と CHIEZO_BASE_URL を書く
docker compose up -d
```

`SECRET_KEY_BASE` は `mix phx.gen.secret` で作る。**64 バイト未満だと起動時に断る**
（通すと起動には成功して全リクエストが 500 になり、原因を追いにくい）。
移行は起動のたびに当たるので、手で流す必要はない。

手元のソースから作り直すときは重ねる。

```bash
docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build
```

ホストで直接動かすなら、DB だけ立てて繋ぐ。

```bash
docker compose -f docker-compose.dev.yml up -d
mix setup && mix phx.server
```

テストは DB が要る。外部への取得はスタブへ差し替えてあるので、ネットワークには出ない。

```bash
docker compose -f docker-compose.dev.yml up -d
mix test
```

**CSS を触ったら焼き直す。** 開発サーバーは watcher を持たない（`config/dev.exs` の `watchers: []`）ので、`assets/css/app.css` を変えても `priv/static` は古いままになる。直したのに画面が変わらないときはここを疑う。

```bash
mix tailwind chidori   # JS も変えたなら mix assets.build
```

アイコンの原本は `priv/static/images/icon.svg`。変えたら PNG を作り直す。

```bash
docker run --rm -v "$PWD/priv/static:/w" -w /w debian:bookworm-slim sh -c \
  'apt-get update -qq && apt-get install -y -qq --no-install-recommends librsvg2-bin \
   && rsvg-convert -w 180 -h 180 images/icon.svg -o images/icon-180.png \
   && rsvg-convert -w 64 -h 64 images/icon.svg -o images/icon-64.png \
   && rsvg-convert -w 64 -h 64 images/icon.svg -o favicon.ico'
```

本番用イメージは `Dockerfile` でビルドする。イメージの中でスタイルと JavaScript も作る。
`main` へ push すると GitHub Actions（`.github/workflows/build-and-push-image.yml`）が
`ghcr.io/rtcode337/chidori:latest` と `:sha-<短縮SHA>` を公開する（amd64 のみ。GHCR には直近の
2 版だけ残す）。パッケージは非公開なので、pull するホストでは `read:packages` の
トークンで `docker login ghcr.io` を済ませておく。

`.env` もリポジトリも置けない環境（管理画面に YAML を貼るタイプ）では
`docker-compose.standalone.example.yml` を `docker-compose.standalone.yml` にコピーし、
値を直書きして貼る（コピーは gitignore 済み）。

基本設計は [docs/basic-design.md](docs/basic-design.md) を参照してください。
採用技術と選定理由は [docs/technology-selection.md](docs/technology-selection.md) を参照してください。
