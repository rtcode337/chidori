# tazuna

日々確認したいニュースや趣味の情報を、利用者ごとの関心に合わせて収集・要約し、適切なタイミングで知らせるアプリです。技術情報に限らず、暮らし、スポーツ、エンターテインメント、地域情報などを扱います。

Elixir と Phoenix で実装し、現在は情報の価値を伝えるトップ画面を表示します。

## Chiezo との関係

tazuna は [Chiezo](https://github.com/rtcode337/chiezo) と利用者のあいだに立つ層です。Chiezo が知識と AI を持つ側で、tazuna がそれを人に見せ、人の意図を向こうへ渡します。

- Chiezo に溜まった情報を、読める形にして見せる（関連図・ニュース）
- 利用者の関心を Chiezo に伝える
- 何を集めてほしいかの指示を Chiezo に渡す（tazuna で読むものも、他のアプリで使うものも）

**名前は手綱から採っています。** 知識と AI を持って走るのは Chiezo の側で、こちらはその様子を見ながら、どちらへ向かわせるかを人が決めるための手元です。

**題材ごとの事情は tazuna が持ちます。** 「画家を集めてネットワーク図にする」のような文脈を Chiezo に持たせると、あちらが題材を選ぶ知識ベースになってしまいます。Chiezo は題材を選ばないまま置き、判断と見せ方はこちらに寄せる、という線引きです。

## 関連図

`/relations` では、画家の影響関係・活躍年代と、人物の家族・コンビ関係をネットワーク図で表示します。**最初に開くのは画家の図**です —— Chiezo に溜めて育てているのはこちらで、人物の図はまだその場で AI に聞く形のためです。

**画家の図は [Chiezo](https://github.com/rtcode337/chiezo) に溜めます。** 「関連図を収集」を押すと、tazuna が Chiezo に**網羅の収集**を依頼し、その場で 1 回集めさせます。作られるのは止まった状態なので、最初の 1 回は Chiezo の管理画面で有効にしてから押してください（止まっている収集は Chiezo が断ります）。有効にすれば Chiezo が決まった間隔でも図を育て、tazuna はそれを読んで表示します。

**名簿・年代・様式は AI に書かせません。** tazuna が条件を言葉で書いて渡し、Chiezo がそれを抽出の指定にして、日本語版 Wikipedia から機械的に引きます（生没年のカテゴリから年代、「〜派の画家」などのカテゴリから様式）。AI が書くのは、そこに書いていないこと —— 影響関係と代表作と説明です。

**丸の大きさは知名度で決めます。** 使うのは日本語版 Wikipedia の月次ページビュー（bot 除外）で、これも Chiezo が収集の 1 件ごとに写してきます（`extra.pageviews_month`）。tazuna は収集を読むだけで図を描けます —— 画家 1 人ずつ引きに行っていた頃は、図を開くたびに数千回の往復が要りました。

**事実と判断は別の鍵に持ちます。** ページビューは機械が写す事実で、誰も書き換えません。日本語版の読まれ方が実態とずれている画家（海外で高名だが日本では読まれない、逆に最近の話題で一時的に読まれている）だけ、AI が倍率（`extra.fame_scale`）を書いて直します。同じ鍵を書き換えさせると元の値が失われ、Wikipedia を取り込み直しても新しいページビューを反映できなくなります。

**名簿は「〜の画家」で終わるカテゴリをまとめて指します**（`tag_suffix`）。書き並べると必ず取りこぼすためです —— 名前の付き方が揃っておらず（「イギリス」と「イングランド」は別のカテゴリで、中身は後者に寄っています）、書く側は思い出しで補うしかありません。**地域も年代も絞りません。** 葛飾北斎とゴッホが同じ図に並びます（ジャポニスムは実際の影響関係です）。

**指定を書けなかったときは収集を作りません。** 指定なしで作ると名簿が空のまま AI に肉付けを頼むことになり、数件だけの図ができて終わります。書けなかった理由は画面に出します。

**誰を見るかは AI に選ばせません。** Chiezo が名簿を区画へ割り、1 回に何区画かずつ渡します。選ばせていた頃は同じ人を何度も選ぶのを止められず、1 日 10 人では一周に何百日もかかりました。区画の切り方と巡回の並びは「画家の図の育て方」にあります。進み具合は画面でも Chiezo の管理画面でも「何区画のうちいくつ回り終えたか」として読めます。

**「ここが間違っている」は割り込みで頼めます**(Chiezo の `POST /v1/collect/<name>/focus`)。定時の巡回の進み具合には触らないので、待たずに直させられます。

**縦軸は年表になっています。** 丸は年代の順に等間隔で並ぶので、目盛りの間隔は一定ではなく、**画家が多い時代ほど広がります**。

**実行のたびに全部を作り直すのではなく、少しずつ良くしていく形**です。1 回で仕上げようとせず、抜けている画家を足す・説明の粗いものを書き直す・粒度を揃える、といった直し方を頼みます。触れなかったものはそのまま残り、消えるのは AI が消すと明示したときだけです。

**図の構造は Chiezo に持ち込みません。** 向こうにあるのは「1 画家 = 1 文書」の普通のソースで、属性と関係はタグに載せてあります。

| タグ | 意味 |
| --- | --- |
| `画家` | この図に取り込む目印 |
| `様式:ポスト印象派` | ノードに添える様式 |
| `年代:1880-1890` | ノード下の年代帯。並び順もこれで決まる |
| `影響元:クロード・モネ:光と色彩` | その画家から受けた影響。線と、線の上の説明になる |

ノードとエッジという読み方を与えるのは tazuna 側です。判断や見せ方を Chiezo に持たせない、という線を崩さないための形にしてあります。

### 見た記録

**丸を押して開いた先で、「見た」印とメモを残せます。** 画家の展覧会へ行った、この絵を実物で見た、といった記録は Chiezo には置けません —— あちらは題材も好みも持たない側なので、利用者ごとの事情は tazuna が持ちます。印の付いたノードは図の上で**橙色の枠**になります（巡回で動いたものの緑の破線とは別の見え方にしてあるので、自分が付けた印かどうかが読み分けられます）。

残るのは「見たかどうか・いつ・ひとこと」の3つで、**1 ノードにつき 1 件**です。印もメモも空にして保存すると記録ごと消えます。**これは暫定の形**で、同じ画家を何度も見に行く記録（展覧会ごとに 1 件）が要るようになったら、この表を親にして子を足す形へ広げます。

**図を開くたびに Chiezo へ聞きに行きません。** 8,000 人ぶんを読むので数秒かかるのに、Chiezo の側は数時間に 1 度しか動きません。見出しの下に**最後に取得した時刻**が出るので、取り直すかは読む人が決めます（「最新の情報を取得」）。

図の左上には**名前で探す欄**と、その隣に**見た画家を選ぶ一覧**が出ます。名前を思い出せなくても、印を付けたところへは戻れます（並びは見た日の新しい順。図に出ていないものは並びません）。

**実在しない見出しを指すタグは、Chiezo が焼く前に落とします**（収集の `verify_tags`）。AI は代表作を挙げられても、それが記事として存在するかは知りません —— 図は「タグがある = 押せば何か出る」として印（◆）を付けるので、混ざっていると押しても何も出ない印が並びます。**画面で取り繕わず、データの側で揃えます**。

**代表作は、説明も絵も Chiezo から引きます。** どちらも jawiki に入っています（取り込みが `page_props` ダンプから代表画像を拾って `extra.image` に入れます）。長期記憶を取り込み直す前は画像が入っていないので、**そのあいだだけ**日本語版 Wikipedia に聞きます（入れば通らなくなります）。**結果は 1 日覚えます**。載せられる画像の無い作品（近年のものはたいていそう）は出しません。絵は原寸ではなく縮小したものを指します。

### 画家の図の育て方

収集は **3 つの巡回**に分かれていて、**順番に意味があります**（後のものは前のものが一周するまで走りません）。

| 巡回 | やること | いつ |
|---|---|---|
| 名簿 | Wikipedia のカテゴリから機械的に名前を集める（AI は使わない） | **一度きり**（取り込み直したら押す） |
| ざっと | **年代と地域**を最優先で埋める。ついでに説明・代表作・様式も。明らかに画家でない人は消す | 1 時間ごと・**一周したら止まる**（2〜3 日） |
| 調査 | 区画ごとに、漏れを足す・内容を磨く・要らないものを消す | ざっとが一周してから。6 時間ごと・**一周 20 日** |

**区画は「地域 × 生年」で切ります。** 辞書順で切っていた頃は「Kage〜おおやちき」のような塊になり、同じ区画に入った 2 人に何の関係もありませんでした。**1 年より細かくは割りません** —— 分けると「この範囲の全員」が並ばなくなり、漏れを問えなくなるためです（人の少ない地域は年の幅が自然に広がります）。

**年代と地域が空だと区画が決まらない**ので、その人は「年代不明」の置き場に入ります。そこを埋めるのがざっとの最優先の仕事で、埋まれば本来の区画へ移ります。

**区画の一覧は図の下（Chiezo の収集の枠）にあります。** まだ見ていないものが先に並ぶので、そのまま「次に回ってくる順」です。**「先に調べる」を押すと、その区画を先に見てもらえます**（印が付くので、巡回が同じところをもう一度見ることはありません）。

**割り込みも調査の回に頼みます**（専用の巡回は置いていません）。画家を名指しした割り込みは区画に印を付けず、区画を名指しした割り込みは印を付けます。

**人物の図は、まだその場で AI に聞く形**です。収集に失敗した場合は、直前の図または表示例を維持し、失敗した理由を画面に出します。

AI の応答に出典が付いていない関係、実在しないノードを指す関係、`http`/`https` 以外の出典は取り込みません。連続して押したときは間隔を空けます。

## 最新情報

`/news` では、[Chiezo](https://github.com/rtcode337/chiezo) の「集める」層に収集を依頼し、溜まったものを読みます。集めるのは Chiezo で、tazuna は依頼と閲覧だけを持ちます。定期実行の時計も、AI の呼び出しも、集めたものの置き場も、すでに Chiezo にあるためです。

**話題ごとにタブで分かれています**（いまは「技術ニュース」と「ニュース」。**先頭のものが最初に開きます**）。**話題は tazuna の機能**で、関連図の「画家」「人物」と同じ立ち位置です。集め方も関心も話題ごとに違うので、定義は `Tazuna.Topics.defined/0` にあります —— 足すときはそこへ 1 つ書けば、タブも収集も増えます。**収集も溜まったものも話題ごとに別**なので、片方を読み直しても、もう片方の状態は入れ替わりません。

**何を集めるかは、話題の「関心」から作ります。** 話題ごとに本文を丸ごと持たせると、話題を足すたびに同じ形の文をもう一度書くことになるためです。関心と名前は定義の側が持ちます（依頼済みの収集の文面を直すのは Chiezo 側から）。

### 流れを追う収集です

Chiezo の収集には**種類**があります。最新情報は**流れ** —— 時とともに増えるものを追っていて、直近だけが対象で、**古いものは順に要らなくなります**（既定で 30 日ぶんを持ち、それより古いものは焼き直しのときに落ちます）。関連図は**網羅**で、ある括りの全部が対象です。増減はしても古いものが要らなくなることはないので、期限では落としません。

### 収集は仕事ごとに分かれています

関連図と同じく、Chiezo に置く収集は**巡回**に分かれています。1 つの文で全部を頼むと、どの回も同じ薄さの仕事になるためです。画面（`/news`）の「Chiezo の収集」の枠で、巡回ごとに頼む相手とモデルと考える量を選んで送れます（モデルと考える量の候補は相手ごとに違うので、相手を選び直すとそちらのものに入れ替わります）。

| 巡回 | やること | AI |
|---|---|---|
| 見出し / 集める | 溜める回。配信元があれば RSS / Atom から機械的に、無ければ AI に集めさせる | 配信元があれば使わない（相手も選べません） |
| 整理 | 前回から入ったものを読んで重要度と分野のタグを付け直し、宣伝や的外れなもの・重複を落とし、**そのうえで**配信元が拾わなかったものを外から探して足す（ニュースだけでなく、話題の記事や論文も） | 使う |
| 要約 | 前回から入ったものを 1 件のまとめにする（箇条書きではなく読み物。出典は記事の見出しでリンクになる） | 使う |

**整理は、まとめより高い頻度で回します**（4 時間ごと / まとめは 12 時間ごと）。まとめの窓に 1 回しか入らないと、直前に起きたことが最大 12 時間ぶん抜けたまままとめられます —— ニュースは新しさが落ちると意味が薄いためです。

**漏れを探す回は分けていません。** 分けていた頃は、重なった時間ぶんを 2 度読ませていました（外を当たる回は直近 4 時間、印を付け直す回は直近 6 時間）。画家の収集が同じ理由で 1 本にまとめてあります（あちらは同じ区画を 3 回渡していました）。**外から見つけたものに、既にあるものを上書きさせない**のだけは依頼文で頼んであります —— 見出しが同じものを薄い要約で返されると、付いている印ごと置き換わるためです。

**技術ニュースは配信元を持っています**（Publickey・ITmedia NEWS・InfoQ Japan・CodeZine・Zenn・Qiita・はてなブックマーク）。見出し・要約・URL・配信日は機械が正確に取れるので、AI の枠は「何が重要か」「どうまとめるか」へ回します。ニュースと記事は同じ収集に溜まりますが、`ニュース` / `記事` のタグで分けて取り出せます。

**溜めるところは機械、選り分けるのは AI**という分担です。配信元から機械的に取り込むぶん、宣伝記事も的外れなものも混ざるので、落とすのは整理の回の仕事にしてあります（落とす力を持つのはこの回だけ）。**消したものは Chiezo が覚えていて**、同じ見出しが次に流れてきても戻りません。

**記事に絵が付くことがあります。** 配信元がフィードで配っているぶんだけです（ページを取りに行くのは本文を取ることになるのでしません）。実測では、はてなブックマークと Zenn が配っています。

**一覧は重要度の順に並びます。** 先頭に出るのは要約の巡回が書いたまとめで、その下に 1 件ずつが「優先 / 注目 / 急がない」の順で並びます。同じ重さのものは新しい順のままです。**低いものも消しません** —— 重要度は並びであって、ふるい分けではないためです。

**重要度は AI が付けた印が先です**（`重要度:高` などのタグ）。付けるのは整理の巡回で、読んだうえでの判断です。語の一致だけで決めると、同じ語を含むだけの 1 件が上に出ます。印が無いものだけ、見出しの語で見ます（災害・避難・金融政策など）。

**押す口は「Chiezo の収集」の枠にある 1 つだけ**です（関連図と同じ形）。収集がまだ無ければ**止まった状態で**作り、あれば画面で選んだ設定を送り直します。**走らせはしません** —— 動き出すのは Chiezo の管理画面で有効にしたときだけなので、**この画面から AI が勝手に動くことはありません**。有効にすると Chiezo が巡回ごとの間隔で集め、tazuna はそれを読みます。

定時の巡回とは別に頼みたいことがあれば、同じ枠の「いま頼む（割り込み）」から 1 回だけ走らせられます（巡回の進み具合にも次の予定にも触りません）。**走るのは整理の回です** —— 専用の巡回は置いていません。頼まれるのはたいてい「これは宣伝だから落として」「この印が違う」で、**落とす力と印を付け直す力を持つのはこの回だけ**だからです。

### まとめを ntfy で知らせます

**画面と通知で、出典の出し方が逆です。** 画面では出典の URL を**記事の見出しでリンク**にします（裸の URL のままだと、押す前にどこへ行くのか読めません）。通知では **URL のまま**渡します —— ntfy が自分でリンクにするので、見出しに差し替えると行き先が読めないただの文字になります。

**飛ぶのは押したときだけです。** tazuna には定時に動く仕組みがまだ無いので、自動では送りません。`/news` の「まとめを知らせる（ntfy）」から「いまのまとめを知らせる」を押します。**押されたときは、知らせ済みでも送ります** —— 押すのは意思表示なので、そこで黙られると「壊れているのか、もう送ったのか」が分かりません（最後に知らせた時刻は画面に出ます）。

**通知先は画面から、話題ごとに決めます。** 宛先は運用しながら変えるもの（試しに別のトピックへ流す、しばらく止める）なので、環境変数だと変えるたびに立て直しが要ります。ntfy の場所だけは環境の事情なので `NTFY_BASE_URL` に既定を置き、話題ごとの上書きも画面からできます。**空にすれば知らせなくなります。** 既定の通知先は持ちません —— 公開の ntfy では、推測できる名前は誰でも読めるためです。

**届かなかったものは知らせた扱いにしません** —— 記録すると、次からは黙って飛ばされ、そのまとめは永遠に届きません。

記事本文は tazuna に保存せず、見出しを押すと Chiezo の中身（要約と出典）が開きます。

Chiezo 側で `CHIEZO_COLLECT_DIR` と `CHIEZO_NOTES_DIR` の両方が設定されている必要があります。

| 変数 | 既定 | 説明 |
| --- | --- | --- |
| `CHIEZO_BASE_URL` | なし | Chiezo のルートURL。未設定ならニュースも関連図もデータ収集も使えない |
| `TAZUNA_NEWS_COLLECTION` | `tazuna_news` | 「ニュース」の話題が使う収集の名前。Chiezo のソース名になる（他の話題の収集名は定義が持つ） |
| `TAZUNA_NEWS_BACKEND` | なし | 収集を頼む相手（`claude` など）。**これは収集ぜんたいの下敷き**で、巡回ごとの相手は画面の表から選ぶ（巡回に書いてあればそちらが勝つ）。未設定なら Chiezo の既定にまかせる |
| `TAZUNA_NEWS_MODEL` | なし | その相手のモデル |
| `TAZUNA_NEWS_EFFORT` | なし | その相手の考える量 |
| `DATABASE_URL` | なし | PostgreSQL の接続先。本番では必須 |
| `TAZUNA_PAINTERS_COLLECTION` | `tazuna_painters` | 画家の図を溜める Chiezo の収集の名前 |
| `TAZUNA_MEALS_COLLECTION` | `tazuna_meals` | 「食事処」を溜める Chiezo の収集の名前（travel-log が読む先） |
| `NTFY_BASE_URL` | なし | ntfy のルートURL の既定。**通知先（トピック）は画面から決める** |

誰に頼むかは本来 Chiezo 側の判断なので、名指しするのは「この収集だけは別の相手に」と決めたときだけです。依頼した後は Chiezo の管理画面からも変えられ、画面には Chiezo が持っている値を出します。

## データ収集

`/datasets` では、**他のアプリで使うデータ**を Chiezo に集めさせる依頼を出します。関連図や最新情報と違い、**この画面は溜まったものを見せません** —— 読むのは使う側のアプリで、こちらが持つのは依頼と進み具合だけです。同じものを 2 つの画面に出すと、どちらが本当の状態なのか読めなくなります。

**集めるものごとにタブで分かれています**（いまは「食事処」）。定義は `Tazuna.Datasets.defined/0` にあります —— 足すときはそこへ 1 つ書けば、タブも依頼も増えます。

### 食事処（travel-log 向け）

travel-log の地図に並べる「食べに行く先」を、日本全国ぶん集めます。**網羅の収集**なので、期限で古いものを落とすことはしません（落とすと地図に穴が開きます）。

**名前と座標は AI に書かせません。** 名簿は Chiezo の 3 つの辞典から機械的に引きます —— 座標を書かせると当てにならない値が混ざり、しかも実行のたびに違う値になります。AI に頼むのは、そこに書いていないことだけです（まだ開いているか・食べに行く先か・どう紹介するか）。

**ひとつの辞典では要る項目が揃いません。** 同じ店が複数の辞典に居たときに、どの項目をどこから採るかまで決めてあります。

| 辞典 | 件数 | 勝つ項目 | なぜ |
|---|---|---|---|
| 百科事典（`jawiki`） | 約 900 | 説明・出典 | 読み物になる紹介文があるのはここだけ |
| 地図辞典（`osm_japan`） | 約 10 万 | 座標・住所・サイト | 現地を歩いた人が置いた点で、いちばん確か |
| 店舗辞典（`overture_japan`） | 約 41 万 | （何も勝たない） | 件数はいちばん多いが、値の確かさは上の 2 つに劣る |

**順位を譲ることと、その値を捨てることは別です。** 百科事典は座標で勝ちませんが、地図に載っていない 1 軒の座標はそこにしか無い —— 捨てると、**その 1 軒はどの区画にも入らず、AI から永遠に見えなくなります**（区画は座標で決まるため）。Chiezo は勝った辞典で埋めたあと、空いたところを残りの辞典で埋めます。

**どの辞典も絞りません。** 網羅の収集なので、機械で引けるものを取りこぼすと、そのぶんを巡回が区画ごとに探し直すことになります —— **機械で済む仕事を AI に払わせる**形です。地図辞典にはもう一段の理由があり、あちらは飲食店にどれも同じ点しか付けないので、件数を書くと並びが見出し順になり、名前が先に来るものだけが残ります（数字と英字の名前が入って、仮名の途中で切れる）。

| | |
|---|---|
| 名簿 | 約 52 万件 |
| 区画 | 約 3,470（1 区画 150 件） |
| Chiezo の素材 | 約 130 MB（1 件 256 バイト） |
| 取り込み時のメモリ | 1.6 GB 前後。**前世代も同時に載るので定常では倍**を見てください |

**一周の長さは、区画の大きさではなく件数で決まります。** AI は 1 件あたり約 1.1 秒（実測）で、Chiezo は区画ごとに 1 回ずつ直列に聞きます —— 52 万件なら、回し続けても 6.6 日が下限です。**区画を大きくしても一周は縮みません**（同じ店を同じだけ読ませるので）。減るのは 1 回ごとの定型文の無駄だけです。

3,470 区画なら、ざっとが 1 日 240 回・**15 日で一周したら止まり**、そのあとはじっくりが 1 日 80 回で回り続けます（一周 43 日）。ざっとの費用は立ち上げの一度きりです。1 回の取り込みは 30〜60 分で、どちらの巡回も次の予定には追いつかれません。

**1 区画の大きさは、入り口ではなく出口で決めています。** この回は残す店ぜんぶにタグと紹介文を付けさせるので、区画の件数がそのまま AI の返す件数になります。実測では **150 件が切れずに全部返り**、47,685 文字・2 分 50 秒でした（1 件あたり約 318 文字）。切れると実害が出ます —— ざっとは一周したら止まるので、返らなかった店は中身が空のまま残り、**次に見られるのは数か月後のじっくり**です。

**同じ店が 2 つに分かれることがあります。** 畳めるのは見出しがそのまま一致したときだけで、実測では、同じ範囲の地図辞典と店舗辞典で名前が一致するのは 3%（60m 以内という条件を足しても 2〜9%）。**畳めなかったぶんは別の 1 件として並びます** —— 気づけるのは区画をまとめて見る AI の回のほうなので、そちらに「1 つにまとめてください」と頼んであります。どちらの値を残すかは 1 件ごとに付いた出典のタグで決めます（座標は `出典:OSM`、説明は `出典:Wikipedia`）。一方、**百科事典の見出しは辞典とよく一致します**（東京都の飲食店 128 件のうち地図辞典に 47 件・店舗辞典に 72 件）。紹介文が要るのはまさにそこなので、この形がいちばん効きます。

**区画は座標で割ります**（店の多いところは細かく、少ないところは粗く）。母集団は集めたもの自身で、対象の矩形には日本全体を書いてあります。

- 母集団を自分自身にするのは、**そのときだけ Chiezo が区画を割り直す**ためです。座標が直れば区画もそれに追随します。
- 矩形を書くのは、**まだ 1 軒も入っていない範囲を対象から落とさない**ためです。点から矩形を作ると点の無いところは矩形の外になり、「ここに足りない店はないか」を永遠に問えません。

| 巡回 | やること | AI |
|---|---|---|
| 名簿 | 3 つの辞典から機械的に引く（一度きり・足すだけ） | 使わない（相手も選べません） |
| ざっと | 区画を一周して、座標を直し・閉店を消し・中身を埋める（一周したら止まる） | 使う |
| じっくり | 区画ごとに、足りない店を探しながら精査する | 使う |

**順番に意味があります。** じっくりはざっとが一周するまで走りません。座標の直っていない状態で「この区画に足りないもの」を問うても、その店は別の区画に居るだけなので、既に入っているものを挙げて終わります。

**押す口は「Chiezo の収集」の枠にある 1 つだけ**です（関連図・最新情報と同じ形）。収集がまだ無ければ**止まった状態で**作り、あれば tazuna が持っている抽出の指定・依頼文・区画の割り方・巡回を送り直します。**走らせはしません**。区画の一覧から「先に調べる」を押すと、その区画だけを先に見てもらえます（定時の巡回の進み具合にも次の予定にも触りません）。

**溜まったものは travel-log が読みます。** 1 店 1 文書で、タグ `食事処` で拾えます。

| travel-log の項目 | 収集の中身 | 誰が入れるか |
| --- | --- | --- |
| 名前 | 見出し | 辞典（同じ見出しは 1 件に畳まれる） |
| 座標 | `extra.lat` / `extra.lon` | 地図辞典が優先（食い違うものだけ AI が直す） |
| 地域 | タグ `地域:<都道府県>` / `extra.area` | 百科事典のカテゴリと地図辞典（無いものを AI が足す） |
| シリーズ / カテゴリ | タグ `ジャンル:…`（**先頭がシリーズ**） | 辞典のカテゴリ（抜けているものを AI が足す） |
| ランク | タグ `ランク:A〜E`（**地図の丸の大きさ**） | AI（`extra.pageviews_month` が目安） |
| 説明 | 本文の 2 行目以降 | 百科事典が優先、無ければ AI |
| 連絡先・公式サイト | `extra.phone` / `extra.website` | 地図辞典が優先 |
| （どの辞典から来たか） | タグ `出典:Wikipedia` / `出典:OSM` / `出典:Overture` | 機械（複数に居た店には複数付く） |

**閉店したものは墓標で消します**（Chiezo が消えた扱いにするタグ）。辞典は閉店をすぐには落とさないので、ここは AI にしか見分けられないところです。消す理由を本文に書かせているのは、消したものは名前が並ぶだけで、理由が無いと消し間違いに気づけないためです。

## 起動

`docker compose` で PostgreSQL ごと立てる。開発サーバーは `http://localhost:7000`。

```bash
cp .env.example .env   # SECRET_KEY_BASE と CHIEZO_BASE_URL を書く
docker compose up -d
```

`SECRET_KEY_BASE` は `mix phx.gen.secret` で作る。**64 バイト未満だと起動時に断る**
（通すと起動には成功して全リクエストが 500 になり、原因を追いにくい）。
移行は起動のたびに当たるので、手で流す必要はない。

手元のソースから作り直すときは重ねる。

```bash
docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build
```

ホストで直接動かすなら、DB だけ立てて繋ぐ。

```bash
docker compose -f docker-compose.dev.yml up -d
mix setup && mix phx.server
```

テストは DB が要る。外部への取得はスタブへ差し替えてあるので、ネットワークには出ない。

```bash
docker compose -f docker-compose.dev.yml up -d
mix test
```

アイコンの原本は `priv/static/images/icon.svg`。変えたら PNG を作り直す。

```bash
docker run --rm -v "$PWD/priv/static:/w" -w /w debian:bookworm-slim sh -c \
  'apt-get update -qq && apt-get install -y -qq --no-install-recommends librsvg2-bin \
   && rsvg-convert -w 180 -h 180 images/icon.svg -o images/icon-180.png \
   && rsvg-convert -w 64 -h 64 images/icon.svg -o images/icon-64.png \
   && rsvg-convert -w 64 -h 64 images/icon.svg -o favicon.ico'
```

本番用イメージは `Dockerfile` でビルドする。イメージの中でスタイルと JavaScript も作る。公開時は `ghcr.io/<owner>/tazuna:<commit-sha>` のようにコミット SHA を含むタグを付ける。
