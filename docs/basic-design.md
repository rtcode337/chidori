# Chidori 基本設計書

> これは作り始める前の構想です。今の実装とは違います（今の形は [README](../README.md) を見てください）。

## 1. 目的

Chidori は、利用者が日々押さえたいテーマや趣味に関する情報を収集し、AI が重要度を判断・要約したうえで通知するアプリケーションである。

技術情報の収集に限定せず、ニュース、地域、金融、スポーツ、エンターテインメント、料理、旅行など、利用者が指定する幅広い関心領域を扱う。情報が多すぎて追い切れない状態を減らし、「今読むべき情報」を短時間で把握できることを目指す。

## 2. 対象利用者と利用シーン

| 利用者 | 利用シーン | 得たい価値 |
| --- | --- | --- |
| 情報収集を習慣化したい人 | 朝や通勤中に一日の要点を確認する | 重要な更新を短時間で把握できる |
| 特定の趣味を追っている人 | 新作、イベント、レビュー、発売情報を追う | 興味のある話題を見逃さない |
| 特定テーマを継続監視する人 | キーワードや情報源の更新を待つ | 変化があった時だけ通知を受け取れる |

## 3. スコープ

### 3.1 初期リリースに含めるもの

- 関心テーマの作成、編集、停止、削除
- キーワード、除外キーワード、カテゴリ、言語、情報源を用いた収集条件の設定
- RSS、公式 API、利用規約上取得可能な公開 Web 情報からの記事・更新情報の収集
- AI による重複統合、分類、重要度付け、要約
- Web アプリ内のフィード表示と、定時・即時のプッシュ通知
- 既読、保存、興味なしの操作と、以後の推薦・通知への反映
- 情報源、収集時刻、原文へのリンクの表示

### 3.2 初期リリースで扱わないもの

- 記事本文の無断転載・全文保存を前提とする機能
- SNS の個人投稿を横断的に収集・再配信する機能
- 売買、予約、応募などをアプリ内で完結する機能
- 医療、法律、投資判断など、高い正確性が必要な領域での助言
- 複数利用者で関心テーマを共同編集する機能

## 4. 用語

| 用語 | 定義 |
| --- | --- |
| 関心テーマ | 利用者が設定する、収集・評価・通知の単位。例: 「好きなバンドの新着情報」 |
| アイテム | 収集した記事、告知、更新情報などの一件 |
| ダイジェスト | 複数アイテムを要約してまとめた配信単位 |
| シグナル | アイテムの重要度、鮮度、利用者との関連度を示す評価値 |
| 情報源 | RSS、公式 API、許諾済みの Web サイトなど、アイテムを取得する入口 |

## 5. ユーザー体験

1. 利用者は、関心のあるテーマを自然文またはキーワードで入力する。
2. アプリは候補となるカテゴリ、関連キーワード、利用可能な情報源、通知頻度を提案する。
3. 利用者は提案を確認・調整して関心テーマを有効化する。
4. 定期収集したアイテムを AI が整理し、重要なものだけをフィードと通知候補にする。
5. 利用者は要約を読み、原文を開く、保存する、既読にする、不要として除外する。
6. 操作履歴を利用し、以後の優先順位と通知量を徐々に調整する。

## 6. 機能要件

### 6.1 アカウント・設定

- 利用者は認証して自分の関心テーマと通知設定を管理できる。
- 通知チャネルごとに有効・無効を設定できる。初期対象は Web Push とメールとする。
- タイムゾーン、通知を避ける時間帯、言語を設定できる。

### 6.2 関心テーマ管理

- 関心テーマには名称、説明、カテゴリ、含めるキーワード、除外キーワード、対象言語、情報源、通知方式を設定できる。
- 関心テーマは「毎日ダイジェスト」「重要時のみ即時」「通知なしでフィードのみ」から通知方針を選べる。
- 利用者が設定を変更した場合、以後に収集するアイテムへ反映する。過去アイテムの再評価は運用上必要な場合だけ行う。

### 6.3 収集・正規化

- 情報源ごとに定めた間隔とレート制限で更新を取得する。
- 原文 URL を正規化し、同一 URL と明確に同一の配信アイテムを重複登録しない。
- 取得内容はタイトル、概要、公開日時、更新日時、原文 URL、情報源、取得日時を基本として保持する。
- コンテンツの取得・利用は情報源の利用規約、robots.txt、API 規約、ライセンスに従う。

### 6.4 AI による整理

- 各アイテムに対し、言語判定、カテゴリ分類、要約、主題キーワード抽出を行う。
- 類似するアイテムをクラスタリングし、一つの話題としてまとめる。
- 関心テーマとの関連度、鮮度、情報源の信頼度、話題の新規性、利用者の反応を加味してシグナルを算出する。
- 要約には、推測と事実を混同しないよう原文にない断定を避ける指示を与える。
- AI の出力失敗時は、原文タイトル・概要・リンクを表示し、配信処理全体を停止させない。

### 6.5 フィード・検索

- ホーム画面では関心テーマ横断の「今日の重要情報」と、関心テーマ別の新着を表示する。
- アイテムには要約、重要と判断した理由、公開日時、情報源、原文リンクを表示する。
- 利用者は既読、保存、興味なしを記録できる。
- 保存済みアイテムと自身のフィードを対象に検索・絞り込みできる。

### 6.6 通知

- 即時通知は、関心テーマ内で定めた重要度閾値を超えるアイテムまたは話題に限る。
- ダイジェスト通知は、未読の重要アイテムを上位からまとめ、指定時刻に送る。
- 同一話題・同一原文・短時間の連続通知を抑止する。
- 配信ログを保存し、利用者は通知を開いたかを確認できる。

## 7. システム構成

実装には Elixir、Phoenix LiveView、PostgreSQL、Oban を用いる。詳細な選定理由とバージョン方針は [technology-selection.md](technology-selection.md) を参照する。

```text
Web / モバイルクライアント
          │
          ▼
       API 層 ───────────── 認証基盤
          │
          ├── 関心テーマ・フィードサービス ── RDB
          │
          ├── 収集スケジューラ ── 収集ワーカー ── 外部情報源
          │                             │
          │                             ▼
          ├── AI 処理ワーカー ── キュー ── 検索インデックス
          │                             │
          ▼                             ▼
       通知サービス ─────────────── 通知プロバイダ
```

| コンポーネント | 責務 |
| --- | --- |
| クライアント | Phoenix LiveView。関心テーマ設定、フィード閲覧、利用者の反応記録、通知許可の管理 |
| API 層 | Phoenix。LiveView と JSON API の提供、認可、入力検証、表示用データの組み立て |
| 収集スケジューラ | 情報源・関心テーマごとの収集ジョブを計画し、キューへ投入 |
| 収集ワーカー | Oban ジョブとして実行。情報源からの取得、形式変換、重複検出、アイテム登録 |
| AI 処理ワーカー | Oban ジョブとして実行。要約、分類、類似話題の統合、シグナル算出 |
| 通知サービス | 通知候補の選定、配信、失敗時の再試行、配信記録 |
| RDB | PostgreSQL。利用者設定、関心テーマ、アイテム、反応、通知履歴、Oban ジョブの永続化 |
| 検索インデックス | フィード・保存済みアイテムの全文検索と絞り込み |

非同期処理はキューを介して分離し、情報源や AI プロバイダの一時的な障害が API 応答に直接影響しない構成とする。

## 8. データ設計（概念モデル）

| エンティティ | 主な項目 | 関係 |
| --- | --- | --- |
| User | id, locale, timezone, quiet_hours | User は Interest を複数持つ |
| Interest | id, user_id, name, description, status, notification_policy | Interest は Rule と Source を持つ |
| Rule | id, interest_id, include_keywords, exclude_keywords, categories, languages | 収集・評価条件 |
| Source | id, type, name, base_url, status, terms_url | 複数 Interest から参照可能 |
| SourceSubscription | interest_id, source_id, config | Interest と Source の関連 |
| Item | id, source_id, canonical_url, title, excerpt, published_at, fetched_at | 収集した原情報 |
| Topic | id, title, summary, category, last_updated_at | 類似 Item をまとめる単位 |
| TopicItem | topic_id, item_id | Topic と Item の中間テーブル |
| InterestItem | interest_id, item_id, relevance_score, importance_score, reason | 利用者ごとの評価結果 |
| UserFeedback | user_id, item_id, type, created_at | 既読・保存・興味なしなど |
| Notification | id, user_id, interest_id, type, status, sent_at | 通知の配信記録 |

`Item.canonical_url` と `Source` の組み合わせに一意制約を設ける。URL が取得できない情報源では、情報源固有 ID を一意キーに用いる。

## 9. 主要な処理フロー

### 9.1 収集から表示まで

1. スケジューラが情報源の更新確認ジョブをキューへ投入する。
2. 収集ワーカーがレート制限を守って情報を取得し、正規化・重複検出後に `Item` を登録する。
3. AI 処理ワーカーが分類、要約、類似話題統合を行う。
4. 各関心テーマのルールと照合し、関連度・重要度・根拠を `InterestItem` として保存する。
5. 通知条件を満たす場合は通知候補を作成し、重複抑止を確認後に配信する。
6. API 層は `InterestItem` を重要度・新しさ・利用者の反応で並べ、フィードとして返す。

### 9.2 フィードバック反映

1. 利用者の既読、保存、興味なしを `UserFeedback` に記録する。
2. 「興味なし」は当該アイテムをフィードから非表示にし、必要に応じて類似キーワードや情報源への評価を下げる。
3. 保存・原文閲覧などの肯定的な反応は、同一関心テーマの関連話題の優先順位へ段階的に反映する。
4. 反応履歴だけで機微な属性を推定・表示しない。

## 10. API 概要

API は HTTPS の JSON API とする。認証済みの API では、すべてのリソースを認証利用者の所有範囲に限定する。

| メソッド | パス | 概要 |
| --- | --- | --- |
| `GET` | `/v1/feed` | 横断フィードを取得する |
| `GET` | `/v1/interests` | 関心テーマ一覧を取得する |
| `POST` | `/v1/interests` | 関心テーマを作成する |
| `GET` | `/v1/interests/{id}` | 関心テーマ詳細を取得する |
| `PATCH` | `/v1/interests/{id}` | 関心テーマ設定を更新する |
| `DELETE` | `/v1/interests/{id}` | 関心テーマを削除する |
| `GET` | `/v1/interests/{id}/items` | 関心テーマ別アイテムを取得する |
| `POST` | `/v1/items/{id}/feedback` | 既読・保存・興味なしを記録する |
| `GET` | `/v1/saved-items` | 保存済みアイテムを取得する |
| `PATCH` | `/v1/notification-settings` | 通知設定を更新する |

## 11. 非機能要件

### 11.1 性能・可用性

- フィード取得 API は通常時の p95 を 500 ms 以下の目標とする。
- 収集・AI 処理・通知は再試行可能なジョブとして設計し、少なくとも一回の実行を前提に冪等化する。
- 外部情報源または AI プロバイダの障害時は、既存フィードの閲覧を維持し、復旧後に未処理ジョブを再開する。

### 11.2 セキュリティ・プライバシー

- 通信は HTTPS を必須とし、保存データはアクセス制御を行う。
- 認可はリソース所有者を必ず確認し、他利用者の関心テーマや反応履歴を取得・更新できないようにする。
- AI プロバイダへ送るデータは、要約・分類に必要な公開情報に最小化する。個人設定や反応履歴を送る場合は、利用目的と送信先を明示し同意を得る。
- アカウント削除時は、利用者設定、関心テーマ、反応履歴、通知先情報を削除または匿名化する。保持期間はプライバシーポリシーに明記する。

### 11.3 コンテンツ・運用

- 原文への導線と情報源を明示し、記事本文は必要最小限の抜粋にとどめる。
- 情報源ごとの利用規約、取得頻度、連絡先、障害状態を管理する。
- AI 要約の誤りを報告できる導線を用意し、問題のある情報源・プロンプト・モデルを追跡できる監査ログを残す。
- 管理者は情報源の停止、再開、取得頻度変更、配信抑止を行える。

## 12. 画面構成

| 画面 | 主な内容 |
| --- | --- |
| オンボーディング | 関心テーマ入力、提案の確認、通知許可 |
| ホーム | 今日の重要情報、未読数、関心テーマ横断フィード |
| 関心テーマ一覧 | 有効な関心テーマ、最終更新、未読数、通知状態 |
| 関心テーマ詳細 | 条件設定、話題別フィード、情報源、通知方針 |
| アイテム詳細 | AI 要約、重要な理由、情報源、原文リンク、反応操作 |
| 保存済み | 後で読むアイテムの検索・整理 |
| 通知設定 | チャネル、時間帯、頻度、関心テーマごとの通知制御 |
| 関連図 | 人物・作品・組織などの関係を、関係種別、方向、時代、出典とともにネットワーク図で表示。手動収集時は Chiezo 経由のAIが公開情報だけを調べ、失敗時は前回の図を維持する |

## 13. 指標

初期運用では、量よりも「役立つ情報を過不足なく届けられているか」を評価する。

- 有効関心テーマ数、関心テーマ作成後 7 日間の継続率
- フィード閲覧率、原文遷移率、保存率
- 通知の開封率、通知停止率、同一話題への重複通知率
- 「興味なし」率、要約の誤り報告率
- 収集成功率、AI 処理成功率、情報源ごとの遅延

## 14. 今後の検討事項

- 初期対応する情報源の選定基準と、情報源追加の審査フロー
- AI プロバイダ、モデル、費用上限、障害時の縮退方法
- 利用者ごとの学習をどこまで自動化し、どの設定を明示的に操作できるようにするか
- モバイルアプリの提供範囲とプッシュ通知基盤
- 話題の信頼性評価、一次情報の優先表示、誤情報対策
- 共同利用、共有関心テーマ、公開関心テーマなどの将来的なソーシャル機能
