# Chidori 技術選定

## 採用構成

| 層 | 採用技術 | 役割 |
| --- | --- | --- |
| 言語・実行基盤 | Elixir 1.20 / Erlang OTP 28 以上 | 並行・障害分離が必要なアプリケーション基盤 |
| Web フレームワーク | Phoenix 1.8 | Web、JSON API、認証、WebSocket の基盤 |
| UI | Phoenix LiveView 1.2 | フィードと設定画面をサーバー主導でリアルタイム更新 |
| 永続化 | PostgreSQL 17 | アプリケーションデータ、全文検索、ジョブ永続化 |
| ORM・マイグレーション | Ecto / Ecto SQL | スキーマ、クエリ、DB マイグレーション |
| 非同期ジョブ | Oban 2.24 | 収集、AI 整理、通知の再試行可能な実行 |
| 配信 | Web Push、メールプロバイダ | 初期の通知チャネル |
| 配布 | Docker / GHCR | 非 root 実行のコンテナイメージ配布 |

## 選定理由

Chidori の中核は、複数情報源の定期取得、AI 処理、通知再試行である。これらは API 要求とは切り離された、失敗を前提とする並行処理である。

Elixir は Erlang VM の耐障害性と並行処理を利用できるため、収集先や AI プロバイダごとに処理を分離しやすい。Phoenix LiveView を使うことで、フィードの既読状態や関心テーマ設定の更新を、別途大規模な SPA を構築せずに実装できる。Oban は PostgreSQL にジョブを永続化するため、収集・要約・通知を同じデータベースを基盤として監視・再試行できる。

既存の C#、Go、Rust、Python、TypeScript、Vue、Kotlin を使ったリポジトリとは異なる、Elixir と HEEx を GitHub の言語統計へ表せる構成とする。

## バージョン方針

2026-09-06 時点で公式リリース・パッケージレジストリを確認し、Elixir 1.20、Phoenix 1.8 系、Phoenix LiveView 1.2 系、Oban 2.24 系を採用対象とする。Phoenix 1.8 は Erlang/OTP 25 以上を必要とするため、コンテナでは保守対象の OTP 28 系を固定タグで利用する。

依存パッケージは `mix.exs` で互換性を保つ範囲指定を行い、ロックファイルをコミットする。コンテナのベースイメージは `latest` を使わず、Elixir と OTP の固定タグを指定する。脆弱性修正を含む更新は定期的に確認する。

## 実装方針

- 単一の Phoenix アプリケーションから開始する。マイクロサービス分割は、明確なスケール要件または独立したデプロイ要件が生じるまで行わない。
- LiveView を基本 UI とし、外部クライアント連携が必要な箇所だけ JSON API を追加する。
- `Accounts`、`Interests`、`Content`、`Notifications`、`Ingestion` の境界で Phoenix Context を分ける。
- 外部 API・RSS の取得、AI 要約、通知配信はすべて Oban Worker とする。各 Worker は冪等にし、タイムアウト、指数バックオフ、ジョブごとの再試行回数を設定する。
- PostgreSQL はアプリケーションと Oban が共有する唯一のトランザクションデータストアとする。検索専用ストアは、検索負荷が実測で問題になるまで追加しない。
- 本番は Docker のマルチステージビルドで release を作成し、非 root ユーザーとして実行する。設定値と秘密情報は環境変数で注入する。

## 採用しないもの

- 初期段階での React/Next.js など、別ビルドパイプラインを持つ SPA
- Redis を必須とするジョブキュー
- 初期段階での Kubernetes、サービスメッシュ、複数サービスへの分割
- AI プロバイダ SDK への強い依存。プロバイダは Adapter 境界の後ろに置く

## 検証環境

この作業環境には Elixir/Mix が未導入である。そのため実装開始時には、固定タグの Elixir/OTP Docker イメージを利用して依存取得、テスト、イメージビルドを行う。ローカル開発用に Elixir を導入する場合も、コンテナと同じメジャー系を使う。
